# Knowledge System 확장 요구사항 명세 v0.1

작성일: 2026-09-29 · 분석 대상: `knowledge-system` `main` @ `1ded9b3e47bc2e09062dba329c2f918423746fa4` · 상태: 구현 전 설계 기준선

이 문서는 [원본 분석과 PDF 원문 대조](./ckv-ckg-ontology-installation-proposal.md), [기술 설계](./spec-driven-architecture.md), [개발 WBS](./spec-driven-wbs.md)의 요구사항 계약이다. 원본 PDF의 페이지는 뷰어 기준이며, 아래 근거 표의 PDF 설명은 **도메인 근거**, 수용 기준은 이 프로젝트에 대한 **새 설계**다. 제품 코드와 실제 성능의 변화는 아직 검증되지 않았다.

## 1. 목표, 경계, 용어

**목표:** AST 기반 코드 그래프(CKG), 자연어·문서 벡터 검색(CKV), 근거 조합(CKS)을 같은 소스 스냅샷에서 일관되게 운용한다. 명시적 개념·관계·증거를 추가해 요구사항→구현→테스트를 추적하고, 임의 프로젝트에 설치 가능한 패키지로 만든다.

**이번 로드맵의 범위:** 감사 정확성, 필터된 검색, 긴 문서 검색, 답 없음 평가, 문서·코드 근거 연결, 소규모 온톨로지, 읽기 전용 변경 계획, 설치·운영 진단. 외부 코딩 에이전트가 생성한 패치는 실행 가능한 스펙 수용 기준으로 검증할 수 있지만 CKS 자체의 자율 코드 수정은 초기 범위 밖이다. 모든 언어에 동일한 AST 충실도를 주장하지 않는다.

**핵심 구별:** `Specification`은 의도한 동작, AST와 소스는 관찰한 구현, `TestResult`는 특정 실행의 결과, `Assertion`은 특정 스냅샷에 대한 근거 있는 주장이다. `proposed` 관계는 검색 후보이고 `verified` 관계만 확정 근거에 사용할 수 있다. CKV의 유사도와 CKG의 경로 존재만으로 요구사항 충족을 증명하지 않는다.

## 3. 기능 요구사항과 수용 기준

각 수용 기준은 정상 경로와 실패 경로를 모두 포함한다. 정량 성능 임계치는 Phase 0에서 실제 기준선을 수집해 [게이트 기록](./spec-driven-wbs.md)에 확정한다. 아래의 `0건`은 정의된 회귀·적대 시나리오 집합에 대한 통과 기준이며 모든 미래 입력에 대한 수학적 보증은 아니다.

|---|---|---|---|
| FR-01 | `ckg audit`는 현재 소스 파일 집합만 집계한다. 역사 변경 `Hunk`의 파일 경로는 현재 파일로 세지 않는다. | 작은 Git 이력 픽스처와 대상 저장소에서 감사가 현재 AST 파일 집합과 일치한다. 과거에만 있던 파일을 새로 추가해도 현재 개수 불변. | 간접: 154쪽의 속성 있는 관계와 시간 맥락; 직접 근거는 코드 재현. |

## 5. 대표 시나리오와 오라클

| 시나리오 | 입력/정답 원천 | 막아야 할 실패 |
|---|---|---|
| S-01 필터 선택도 | 특정 커밋·경로·언어 안의 관련 청크, 필터된 정확 검색 결과 | 전역 상위 3K에 없다는 이유로 누락 |
| S-02 긴 문서 끝 | 한 제목 아래 긴 Markdown의 마지막 단락과 정확 줄 | 앞부분만 색인, 부모 줄을 잘못 인용 |
| S-03 과거 Git 파일 | 현재 없는 파일을 포함한 `Hunk` 이력 | 감사가 과거 파일을 현재 파일로 세는 오류 |
| S-04 답 없음 | 저장소에 존재하지 않는 API·정책을 묻는 질문 | 무관한 인용을 달고 단정, 평가 점수 1.0 |
| S-05 스펙-코드 충돌 | 스펙 문장과 AST 조건이 다른 고정 픽스처 | 스펙 또는 코드를 조용히 진실로 승격 |
| S-06 모호한 용어 | 같은 용어의 두 개념/한영 별칭/미등록 표현 | 첫 매칭을 하드 필터로 강제해 올바른 검색 결과 제거 |
| S-07 복수 프로젝트 | 동명 심볼이 다른 두 저장소 | 출처 혼합, 다른 프로젝트의 테스트를 검증 근거로 사용 |
| S-08 작업 트리 | 같은 HEAD에서 수정 파일 및 새 파일 | HEAD만으로 같은 버전이라고 표시 |
| S-09 승격 실패 | 그래프 완료·벡터 실패 등 주입 | 부분 데이터셋을 `current`로 노출 |

시나리오마다 `query`, `project_id`, `snapshot`, 필터, 기대 청크/경로/인용/기권 상태를 고정 파일로 기록한다. 생성 답변을 문자 일치로만 채점하지 않고, 근거와 관계 경로의 유효성을 독립 검증한다. 평가셋은 온톨로지 없는 기준선과 새 경로에 동일하게 적용한다.

## 7. 변경 통제

요구사항은 `제안 → 리뷰 → 승인된 기준선 → 구현 → 검증 결과` 상태로 관리한다. WBS 작업은 관련 FR/INV/NFR과 실패 시나리오를 먼저 지정하고 시작한다. 구현 중 새 결함이 발견되면 테스트·수용 기준을 먼저 수정한 뒤 패치한다. 수치 임계치나 데이터셋 정의를 변경하려면 변경 이유, 비교 가능한 구버전 결과, 승인자를 기록한다. 미완료 항목은 검증된 기능으로 표시하지 않는다.
