# 방향 검토: 무엇을 고치고 무엇을 만들 것인가 (2026-11-13)

이 문서는 2026-11-13 대화에서 나온 두 검토를 합친 기록이다. 하나는 설계 의도와 구현의 차이를 짚고 연구 방향을
제안한 검토이고, 다른 하나는 관련 연구의 평가 방식과 작업 순서를 다룬 검토다. 그 뒤 같은 날 확인한 결과
(그래프 검증, D2 수정, P1 판정)와, 사용자가 낸 제안 가운데 합의한 것(10장), 단계별 계획(11장)을 반영했다. 실행 순서와 상태의 정본은 [정확도 로드맵](../ACCURACY-ROADMAP.md)이다.
이 문서는 왜 그 순서가 되었는지를 남긴다.

## 1. 출발점: 사용자가 밝힌 설계 의도

1. LLM은 똑똑해도 기업의 개별 프로젝트를 깊이 알지 못한다. 그래서 slop과 환각이 생긴다. 이 시스템은 LLM이
   프로젝트를 더 정확히 이해하게 돕는 지식 체계이고, 제품 개발과 유지보수 자동화의 출발점이다.
2. 코드는 AST로 파싱해 그래프로 만든다. 컴파일과 링크 시점에는 변수와 함수가 실제 주소로 이어지므로, 코드끼리의
   연결이 가장 분명해진다. 그 연결을 그래프로 옮겨, 코드가 무엇에 영향을 받고 무엇에 영향을 주는지 알게 한다.
3. 코드에는 결과만 남고 "왜 그렇게 되었는가"는 남지 않는다. 주석도 약하다. 의도를 모르면 맞는 코드를 틀렸다고,
   틀린 코드를 맞다고 판단하게 된다. 이 암묵지는 벡터 DB에 담는다.
4. 두 DB는 서로 이어져야 한다. 벡터에서 찾은 것을 그래프의 코드에 잇고, 그래프의 결과로 벡터를 검색한다.
5. 같은 산업의 서로 다른 프로젝트에서도 같은 검색 경험을 주려고 온톨로지를 도입했다. 지금은 효과가 없다.

목표는 결정론적으로 DB를 만들고, 일반화된 프로젝트로 만드는 것이다. 사용자는 또 "Attention Is All You Need"처럼
기존 방식 대비 성능과 정확도를 보이고 싶다고 했다.

## 2. 핵심 판단

**"코드가 어디 있는가"를 찾는 일보다 "왜 그렇게 되어 있는가"를 코드에 묶어 주는 일에 무게를 옮긴다.**
단, 그 전에 **이미 만들어진 데이터가 맞는지부터 검증하고 고친다** (사용자 결정. 원문: "이미 생성된 데이터
부터 문제가 있으면 당연히 결과가 좋지 않자나").

근거는 P1 실측이다(로드맵 4.5). go-stablenet 버그 수정 7건을 진단 에이전트로 42번 돌렸다.

- 근본 원인은 41번 맞혔다. 팩을 요청하지 않은 11번도, 팩에 정답 본문이 없던 실행도 grep과 파일 읽기로 찾았다.
  위치 찾기는 이 에이전트에게 이미 쉬운 일이다.
- 틀린 실행은 두 종류였다. pr-70의 한 실행은 근본 원인을 다른 곳(`InsertReceiptChain`)으로 지목했다.
  pr-77의 한 실행은 "의도적으로 유지하는 트랜잭션별 tip 캐시를 지우라"고 제안했다. 둘째는 위치가 아니라 의도를
  몰라서 틀렸다.
- 그 의도는 이미 도메인 항목으로 적혀 있다(#132, "트랜잭션별 tip 캐시는 재주입 사이에도 의도적으로 유지").
  그런데 팩을 만드는 경로가 이 항목을 따라가지 않는다(3장).

## 3. 설계 의도와 구현의 차이

1장의 의도를 코드와 대조했다. 구현이 의도에 가장 못 미치는 곳이 "왜"와 "연결"이다.

| 의도 | 구현 상태 | 가장 큰 빈틈 |
|---|---|---|
| 링커가 보는 연결을 그래프로 | Go는 go/types까지 쓰는 파서, 노드와 엣지 종류가 풍부함 | 인터페이스 호출이 구현체로 이어지지 않음. 함수 값 호출은 대상이 없음. 이름 해석 결함(4장) |
| 영향을 주고받는 관계를 명확히 | `calls`, `implements`, `writes_field` 등 | `reads_field`와 `references`는 정의만 있고 만들어지지 않음 |
| 암묵지(왜)를 담는 곳 | PR, 커밋, ADR, invariant, 도메인 항목이 벡터 색인에 들어감 | 대부분 코드와 묶여 있지 않음 |
| 두 DB의 연결고리 | 청크마다 `canonical_id` 하나 | 한 방향, 일대일. 그래프에서 벡터로 가는 조회가 없음 |
| 온톨로지로 일관된 경험 | 데이터 모델과 저장소는 있음 | 검색 경로에 연결돼 있지 않음(6장) |

### 그래프: 링커 관점에서 빠진 것

"컴파일과 링크 시점에 연결이 분명해진다"는 착안에 비춰 보면, 정적 호출은 잘 잡고 동적 연결은 끊겨 있다.

- **인터페이스 호출**: `invokes` 엣지가 인터페이스의 메서드 노드에서 멈춘다. 실제로 실행될 구현체로 이어지지
  않는다.
- **함수 값과 콜백**: 대상 없는 자기 자신 엣지로 기록된다. Go에서 등록 패턴과 핸들러는 대부분 이 형태다.
- **읽기 관계**: 필드 엣지는 쓰기만 만든다. "이 값은 어디서 쓰이나"를 그래프로 답할 수 없다.
- **빌드 대상**: 빌드 태그 없이 호스트 OS 기준으로 읽는다. `--files-from-main`은 파일 단위이고, 실제 바이너리에
  들어가는 심볼 단위가 아니다.
- **이미 있는 자산**: 정의-사용, 도달 정의, 제어 의존 분석이 질의 시점 도구로 있다(`pkg/graph/valueflow`).
  그래프에 저장되지 않아 검색 단계가 쓰지 못한다.

### 왜(결정) 지식: 있지만 코드에 묶이지 않음

- PR 청크는 가짜 경로(`pr/저장소#번호`)를 가져 어떤 함수와도 이어지지 않는다. 파일 단위 목록만 남는다.
- ADR과 문서는 코드와 연결이 없다.
- 도메인 항목(검증된 42개)은 그래프에 `Policy` 노드와 `governed_by` 엣지로 들어간다. 이 엣지는
  `policy_security` 도구 하나에서만 읽고, 팩을 만드는 경로는 따라가지 않는다.
- 그래프에는 줄 단위 PR 연결표(`node_prs`)가 이미 있다. Stage 3은 이것을 쓰지 않는다. 함께 바뀌는 코드
  (co-change) 엣지는 없다.

### 연결고리: 한 방향, 일대일

벡터 청크가 그래프 노드 하나를 가리킬 뿐이다. "이 함수를 설명하는 PR, 결정, invariant를 모두 달라"는 반대
방향 조회가 없다. 1장의 "graph의 결과로 vector를 검색한다"는 흐름이 구현되지 않았다.

### 결정론의 빈틈

- LLM 접두어의 캐시 키에 모델 이름이 없다. 모델을 바꿔도 예전 접두어가 재사용된다.
- 요약 모델이 manifest에 기록되지 않는다.
- 이름 해석의 접미사 대체가 Go 맵 순회로 첫 일치를 골랐다. 같은 입력에서 빌드마다 다른 엣지가 나올 수
  있었다(4장, D2에서 고침).

## 4. 데이터 검증: 처음 생각보다 데이터가 틀려 있었다

### 수동 점검

PR 74 기준 커밋의 색인 하나를 읽기 전용으로 살폈다. 원본 소스와 대조해 틀린 연결 세 건을 확인했다.

1. **`core.Genesis`**: 진짜 구조체(`core/genesis.go:58`)로 들어오는 참조가 0개였다. 140개 모두 생성 코드
   (`core/gen_genesis.go:21`)의 `MarshalJSON` 안에 선언된 같은 이름의 지역 타입을 가리켰다.
   `core.SetupGenesisBlock`, `core.initializeAnzeonGenesis`가 여기에 들어간다.
2. **`handleTransactions`**: `eth/handler_eth.go`의 `Handle`은 같은 패키지의 함수를 부르는데, 그래프는
   다른 패키지(`eth/protocols/eth`)의 소문자 함수로 이었다. Go에서 불가능한 호출이다.
3. **`PairingCheck`**: `core/vm/contracts.go`는 `crypto/bn256`의 함수를 부르는데, 그래프는
   `crypto/bn256/cloudflare`로 이었다.

원인은 같았다. 짧은 이름(`패키지.이름`)으로 찾을 때 같은 이름이 둘이면 하나가 다 가져간다.

벡터와 그래프의 연결은 대체로 건강했다. 다른 이름의 노드에 묶인 심볼 청크는 10,806개 중 45개였다. 다만 파일
머리 청크(import 블록) 668개 중 650개가 파일의 첫 선언에 묶여 있었다. 코드 주석은 "건너뛴다"고 적고 있다.

### 검증기로 전수 측정

수동 점검의 숫자는 무늬로 찾은 하한이었다. 그래서 고치기 전에 전체 크기를 쟀다. `ckg verify`가 그래프를
go/types의 해석과 대조한다([Go 그래프 검증](../graph/GO-GRAPH-VERIFICATION.md)).

| 지표 (PR 74 기준 커밋) | 고치기 전 | D2·D3 뒤 |
|---|---|---|
| 정적 호출 재현율 | 0.9765 | 0.9886 |
| 잘못 이어진 정적 호출 | 7 | 2 |
| 함수 리터럴 밖에서 빠진 호출 | 326 | 5 |
| 잘못 이어진 타입 참조 | 357 | 6 |
| go/types가 뒷받침하지 않는 호출 엣지 | 931 | 126 |
| 패키지 수준 id를 가진 지역 선언 | 123 | 0 |

남은 것은 함수 리터럴(고루틴, 클로저) 안의 호출이 빠지는 문제(D4)와 타입 참조 범위다.

## 5. 개선 방향

### 순서

| 단계 | 하는 일 | 기준(무엇과 대조하나) |
|---|---|---|
| 0-가. 그래프 검증 | 선언이 빠짐없이 있는가, 호출·타입 참조·구현 관계가 맞는가 | go/types, 표준 호출 그래프 분석 |
| 0-나. 벡터와 연결 검증 | 심볼마다 청크가 있는가, 연결이 맞는가 | 그래프 노드의 줄 범위와 이름 |
| 1. 결합 로직 검증 | 정답을 아는 질문으로 단계마다 어디서 정답을 잃는지 추적 | 고정된 정답과 단계 기록(`CKS_DEBUG_TRACE`) |
| 2. 결정 지식을 심볼에 묶기 | 아래 A | 의도를 묻는 과제(12장) |

- 0단계는 LLM도 사람의 라벨도 필요 없다. 기준이 컴파일러라 객관적인 숫자가 바로 나온다.
- 데이터와 로직이 어긋난 곳도 1단계 대상이다. 예: Stage 3은 의도에 따라 `references` 관계를 요청하는데, 그
  엣지는 데이터에 없다.
- 주의: 끝이 없을 수 있으므로 점검 항목과 통과 기준을 시작 전에 정한다. 고쳐도 검색 결과가 그대로일 수 있으므로
  결함마다 "팩이 바뀌는가"를 기록한다. Go 밖의 언어는 기준이 약하다.

### A. 결정 지식을 심볼에 묶는다 (데이터 검증 뒤 1순위)

1. 연결을 다대다로 바꾼다. 청크와 심볼 사이에 역할이 붙은 연결을 둔다(정의, 설명, 변경, 제약, 시험). 로드맵의
   J1이다.
2. PR을 바뀐 함수에 묶는다. 줄 단위 연결표(`node_prs`)가 이미 있어서 결정론적으로 된다.
3. 근거 문장을 뽑는다. PR 본문, 리뷰 토론, 이슈에서 목표, 필요, 기각한 대안을 별도 청크로 둔다. LLM이 필요하므로
   원문 인용이 붙은 것만 남긴다.
4. 팩에 "제약" 칸을 둔다. 고른 함수에 묶인 결정과 invariant를 본문과 따로 돌려준다. 지금의 knowledge 예약 2칸을
   "이 함수에 묶인 것"으로 좁힌다.

재료(PR 연결표, 도메인 항목, invariant)가 이미 있어서 첫 단계는 새 추출 없이 연결만으로 만들 수 있다.

### B. 그래프를 링커 관점에 맞춘다

1. 인터페이스 호출을 구현체로 확장한다. Go 표준 호출 그래프 분석(RTA, VTA)으로, `main`에서 도달할 수 있는
   구현체로만 좁힌다.
2. 등록 패턴을 엣지로 만든다. 맵에 넣는 핸들러, 인자로 넘기는 함수 값이다. "새 하드포크는 어디에 등록하나"(pr-63)
   같은 질문이 이 엣지로 풀린다.
3. 읽기 엣지와 참조 엣지를 실제로 만든다.
4. 도달 가능한 심볼을 표시해, 바이너리에 들어가지 않는 코드를 검색에서 뒤로 미룬다.

### C. 온톨로지를 후보를 만드는 단계로 옮긴다

1. 질문의 낱말을 개념으로, 개념을 심볼로 잇고, 개념에 묶인 심볼을 Stage 1 후보로 직접 넣는다.
2. 묶음을 구조에서 제안한다. 그래프의 구조적 역할(진입점, 등록 지점, 상태 전이 함수, 검증 함수)을 규칙으로
   찾아 후보를 내고 사람은 승인만 한다.
3. 프로젝트 간 공통어를 구조 역할로 잡는다. "합의 메시지 처리기", "포크 활성화 지점" 같은 역할은 비슷한 체인
   프로젝트에 모두 있다. 낱말 사전보다 이 분류가 "일관된 검색 경험"에 가깝다.
4. 낱말 매칭을 임베딩으로 바꾼다. "쿼럼"과 "정족수"가 같은 개념에 닿아야 한다.
5. 평가의 오염을 없앤다. 온톨로지를 켜면 용어 확장이 함께 꺼지는 결합을 풀어야 효과를 잴 수 있다.

### D. 질의 알고리즘

- **개인화 PageRank**: 찾은 심볼에서 그래프를 따라 점수를 퍼뜨린다. A와 B로 엣지가 늘면 효과가 커진다(HippoRAG).
- **묶음 요약**: 그래프 군집마다 요약을 두어 넓은 질문에 답한다(GraphRAG).
- **에이전트가 쓰는 도구로 설계**: 팩 하나를 통째로 주기보다 에이전트가 그래프를 한 걸음씩 따라가는 도구가 맞을
  수 있다(LocAgent). P1에서 에이전트는 팩을 받고도 grep을 4~13회 더 했다.

## 6. 온톨로지가 영향이 없는 이유

1. 기본값이 꺼져 있다(`OntologyMode`의 기본 `off`).
2. 켜도 Stage 2에서 이미 뽑힌 후보의 점수를 최대 1.2배 올릴 뿐이다. 새 후보를 넣지 못하고 질의도 고치지 않는다.
3. 개념을 코드에 묶는 `IMPLEMENTED_BY` 관계를 만드는 Go 코드가 없다. 실제 저장소에 검토된 연결은 0개다.
4. 승인된 개념이 4개이고 모두 WBFT 합의 영역이다.
5. 낱말이 글자 그대로 같아야 걸린다. 첫 평가에서 288번 실행이 모두 `no_match`였다.
6. 온톨로지를 켜면 Stage 1의 용어 확장이 함께 꺼져, 켜고 끈 비교가 오염돼 있다.

## 7. 관련 연구와 평가 방식

### 연구별 평가

| 연구 | 과제와 표본 | 정답의 출처 | 지표 | 판정 주체 |
|---|---|---|---|---|
| LocAgent | 고칠 위치 찾기. SWE-bench Lite 274건, Loc-Bench 560건 | 실제 수정 패치가 바꾼 함수 | Acc@k(정답 위치가 모두 상위 k 안), NDCG | 자동 대조 |
| RepoGraph | 이슈 해결. SWE-bench Lite 300건 | 저장소의 시험 | 해결률, 위치 일치율, 비용 | 시험 실행 |
| CodexGraph | 이슈 해결 257건, 코드 완성 1,000건, 코드 생성 212건 | 시험, 원래 코드 | 해결률, 완전 일치, 편집 유사도 | 시험 실행, 문자열 대조 |
| GraphCoder | 다음 줄 완성 8,000건 | 지워 둔 원래 줄 | 완전 일치, 편집 유사도, 식별자 일치 | 문자열 대조 |
| HippoRAG | 다단계 질의응답. 3개 데이터셋에서 1,000문항씩 | 사람이 표시한 근거 문단, 기준 답 | Recall@2/5, EM, F1 | 자동 대조 |
| GraphRAG | 문서 전체를 묻는 질문 125개씩 2개 말뭉치 | 정답 없음. 질문도 LLM이 생성 | 포괄성, 다양성 등 승률 | LLM이 두 답을 비교(5회) |
| Argus | 커밋의 변경 이유 뽑기. 평가 커밋 50건 | 연구자 2명의 문장 단위 주석(κ 0.786) | 정밀도, 재현율, F2 | 사람 |
| SWE-Shield | 수정이 설계 제약을 지키는가. 이슈 495건, 제약 1,787개 | PR 리뷰에서 LLM이 뽑고 사람이 표본 검증(90.4% 유효) | 시험 통과율과 제약 충족률을 따로 | LLM 3개 다수결(사람과 80.8% 일치) |
| Is Grep All You Need | 긴 대화 기록에서 답 찾기 116문항 | 기준 답 | 정확도 | LLM 채점 |

SWE-Shield 벤치마크의 제약 추출 도구 이름이 DesignHunter다.

### 네 갈래

- **정답 위치와 자동 대조**: LocAgent, HippoRAG의 검색 평가. 이 프로젝트의 "정답 함수가 팩에 들었나"가 여기에 속한다.
- **시험을 돌려 판정**: SWE-bench 해결률. 가장 객관적이지만 위치 찾기와 수정 능력이 섞인다.
- **기준 답과 문자열 대조**: 코드 완성 계열. 뜻이 같아도 글자가 다르면 틀린 것으로 센다.
- **사람이나 LLM이 판정**: GraphRAG, Argus, SWE-Shield. P1의 C1~C4 판정이 여기에 속한다.

### 숫자를 읽을 때

- 같은 벤치마크라도 표본이 다르다. SWE-bench Lite를 LocAgent는 274건, CodexGraph는 257건, RepoGraph는 300건으로 썼다.
- CodexGraph와 RepoGraph는 한 번 돌린 결과다. RepoGraph의 향상은 300건에서 2~3점이다(예: 27.33 → 29.67).
- LocAgent 저자들은 SWE-bench가 학습 자료와 겹칠 수 있다고 보고, 2024년 10월 이후 이슈로 Loc-Bench를 만들었다.
- SWE-Shield에서 시험 통과율은 70~76%인데 제약 충족률은 33~43%였다. 둘의 연관은 거의 없었다(Cramér's V 0.12 이하).

### 비어 있는 자리

- 그래프를 만드는 6편 가운데 5편은 그래프 자체의 정확도를 재지 않았다. 최종 과제 점수로만 간접 평가한다.
  HippoRAG만 작은 규모(문서 20개, 삼중항 239개)로 쟀다. `ckg verify`가 이 자리를 채운다.
- 결정 근거를 검색해 코드 이해 질문에 답하는 것을 직접 평가한 연구는 찾지 못했다.
- 프로젝트 간 온톨로지 재사용을 소프트웨어 공학에서 평가한 연구도 찾지 못했다.

수치는 각 논문 원문의 평가 절에서 확인했다. 결과 표 전체를 대조하지는 않았다.

## 8. 기존 방식 대비 성능을 보이려면

- **지금의 한계**: 표본이 go-stablenet 11건, indexer-go 26건이고, 정답 라벨은 AI가 붙였으며 사람 확인 전이다.
  위치 찾기는 P1에서 천장에 닿았다.
- **비교 대상**: grep만 쓰는 에이전트, 벡터만, 그래프만, 결합, 그리고 공개된 방법(LocAgent 등).
- **공개 벤치마크**: SWE-bench Lite 위치 찾기가 표준이다. 공개 저장소라 모델이 답을 미리 알 수 있다.
- **고유 벤치마크**: 비공개 프로젝트에서 "의도를 아는가"를 재는 과제가 필요하다. 수정 방향이 기존 결정과
  어긋나지 않는가(P1의 C3), 바꾸면 무엇이 깨지는가, 이 코드는 왜 이렇게 되어 있는가. LLM의 일반 지식으로 풀 수
  없어서 지식 시스템의 기여가 그대로 드러난다.
- **제거 실험**: 구성 요소를 하나씩 끄고 재는 표가 있어야 어느 부분이 기여하는지 보일 수 있다.

## 9. second brain 구상에 대한 의견

"LLM은 인류 전체의 지식, knowledge-system은 특정 팀의 지식"이라는 구분은 맞는 방향이다. 성립하려면 세 가지가 필요하다.

1. **출처와 검증 상태**: 누가 언제 확인했는지가 값의 일부다. 도메인 항목의 `verified` 상태가 그 씨앗이다.
2. **낡음의 관리**: 코드가 바뀌면 묶인 결정도 다시 확인해야 한다. 지금은 줄 번호 밀림만 잡고, 이름이 바뀌면 끊긴다.
3. **모른다는 표시**: 검증된 지식이 없는 곳은 없다고 말해야 한다. v2 계약의 `Unknowns`가 이 역할이다.

## 10. 사용자 제안과 합의한 내용

같은 기간 대화에서 사용자가 낸 제안 가운데 합의한 것을 남긴다. 원문은 사용자 메시지 그대로, 합의 범위와 조건은
대화에서 정한 그대로다.

| 제안 (사용자 원문 요지) | 합의한 것 | 조건과 상태 |

## 11. 단계별 진행 계획

각 단계는 앞 단계의 측정으로 끝을 판정한다. 측정 없이 다음 단계로 넘어가지 않는다.

### 0단계. 데이터 정확성 (진행 중)

- 0-가. 그래프: D2, D3 완료. 남은 것은 D4(함수 리터럴 안의 호출: 정적 306개, 인터페이스 59개), D5(타입 참조 범위,
  `reads_field`와 `references`). 판정: `ckg verify`의 재현율과 잘못 이어짐 수.
- 0-나. 벡터와 연결: ckv 쪽 검증기를 만든다(심볼마다 청크가 있는가, 연결이 맞는가, 잘린 청크). 알려진 결함은 파일
  머리 청크가 첫 선언에 묶이는 것과 묶인 `var (...)` 블록(D6).
- 0-다. 색인 재빌드: go-stablenet 기준 커밋 11개를 고친 그래프로 다시 만든다.
- 0-라. 언어 추상화 검토: 파서 프런트엔드(Go, Solidity, TypeScript, Proto)가 공유해야 할 계약을 정리한다. 심볼 정체성
  (canonical id) 규칙, 엣지 종류와 그 뜻, 동적 호출의 표현, 검증기가 쓰는 참값의 인터페이스다. Go에서 고친 결함 종류
  (짧은 이름 충돌, 지역 선언의 id, 접미사 대체)가 다른 언어 프런트엔드에도 있는지 같은 기준으로 점검한다. 언어마다
  컴파일러 수준의 참값이 없는 경우(Solidity, TypeScript)에 쓸 대체 기준도 정한다.
- 끝: 그래프와 연결의 알려진 결함 종류마다 수치가 기준 아래이고, 재빌드한 색인에서 사례의 팩이 어떻게 바뀌었는지
  기록되어 있다.

### 1단계. 결합 로직 디버깅

- 정답을 아는 사례(go-stablenet 11건, indexer-go는 고정 입력을 옮긴 뒤)로 단계 기록(`CKS_DEBUG_TRACE`)을 남기고,
  정답을 잃는 단계를 찾는다.
- 데이터와 로직의 불일치를 고친다(D7. 예: Stage 3이 만들어지지 않는 관계를 요청).
- MCP 사용 검증의 제품 쪽 부분과 첫 탐색 단계 규칙(스킬 검토 세션)을 넣는다.
- 끝: 사례마다 정답을 잃는 단계와 이유가 기록되어 있고, 고칠 수 있는 것은 고쳤다.

### 2단계. 결정 지식을 심볼에 묶기 (5장 A)

- 연결 표를 다대다로(J1). PR을 바뀐 함수에 묶는다(`node_prs`). 도메인 항목의 `governed_by`를 팩 경로로 잇는다.
- 팩에 "제약" 칸을 두어, 고른 함수에 묶인 결정과 invariant를 따로 돌려준다.
- 근거 문장 추출은 원문 인용이 붙은 것만 남긴다.
- 끝: "의도를 아는가" 과제(12장)를 만들고, 묶기 전후를 같은 과제로 잰다. pr-77의 tip 캐시 같은 의도 위반이 줄어야 한다.

### 3단계. 그래프를 링커 관점에 맞추기 (5장 B)

- 인터페이스 호출을 도달 가능한 구현체로(VTA), 등록 패턴 엣지, 도달 가능성 표시.
- 끝: `ckg verify`에 동적 호출 항목을 더해 재고, "어디에 등록하나" 유형(pr-63)의 팩이 바뀌는지 본다.

### 4단계. 온톨로지 재설계와 질의 알고리즘 (5장 C, D)

- 온톨로지를 후보를 만드는 단계로 옮기고, 구조 역할로 프로젝트 간 공통어를 잡는다. 켜고 끈 비교의 오염을 먼저 푼다.
- 개인화 PageRank, 묶음 요약, 에이전트용 한 걸음 도구를 잰다.
- 끝: indexer-go를 홀드아웃으로 D6 규칙에 따라 판정한다.

### 5단계. 기존 방식 대비 평가

- 제거 실험 표(그래프만, 벡터만, 결합, 각 구성 요소 끔), grep만 쓰는 에이전트와의 비교.
- 논문과 같은 지표를 LLM이 모르는 코드에서 잰다(13장). 공개 벤치마크(SWE-bench Lite)는 참고로만 쓴다.
- 끝: 같은 저울 위에서 기존 연구와 나란히 놓을 수 있는 표가 있다.

## 12. "의도를 아는가" 과제: 의도가 적힌 PR로 시험한다

사용자 제안(2026-11-13): PR 가운데 어떤 문제에서 어떤 의도로 수정 방향을 결정했는지 적어 둔 것으로 시험한다.

- **고르는 규칙**: 머지된 PR 가운데 본문이나 리뷰 토론에 결정의 근거가 적힌 것. 예: 기각한 대안, 지켜야 하는 제약,
  "이렇게 하지 않은 이유". 규칙은 결과를 보기 전에 고정한다.
- **정답**: PR에 적힌 결정과 제약 그 자체다. AI가 문장을 뽑을 수는 있지만, 정답으로 쓰기 전에 사람이 원문과 대조해
  확인한다. Argus 연구는 같은 추출에서 정밀도가 51.4%였으므로 확인 없이 쓰지 않는다.
- **질문**: 증상만 담은 문제 문장. 결정이나 해법은 넣지 않는다(P1과 같은 규칙).
- **판정**: 진단 결과의 수정 방향이 PR의 결정과 제약을 지키는가(P1의 C3를 넓힌 것), 기각된 대안을 제안하지 않는가.
  SWE-Shield가 쓴 "제약 충족, 위반, 해당 없음" 구분을 따른다.
- **누설 주의**: 색인과 지식은 PR 기준 커밋 이전의 정보만 담는다. 그 PR 자체의 본문은 색인에 넣지 않는다.
- **후보 원천**: go-stablenet과 indexer-go의 PR, 같은 조직의 다른 저장소. 어느 PR에 근거가 적혀 있는지는 아직 세지 않았다.

## 13. LLM이 모르는 코드로 논문과 비교할 준비

사용자 제안(2026-11-13): 논문이 쓴 공개 코드가 아니라 LLM이 모르는 프로젝트 코드로, 논문의 결과값과 비교할 수
있게 준비한다.

- **왜**: SWE-bench 같은 공개 벤치마크는 모델이 학습했을 수 있다(LocAgent 저자들도 지적). 이 시스템이 겨냥하는 것은
  LLM이 모르는 팀의 코드다. 그 조건에서 재야 이 시스템의 기여가 드러난다.
- **"모른다"의 기준**: 비공개 저장소이거나, 공개라도 평가에 쓰는 모델의 학습 시점 이후에 머지된 PR. 표본마다 어느
  기준으로 골랐는지 적는다.
- **논문과 같은 저울**:
  - 위치 찾기: LocAgent의 Acc@k(파일, 모듈, 함수 단위, 정답 위치가 모두 상위 k 안에 있어야 성공). 정답은 수정
    패치가 바꾼 함수다. 이 프로젝트의 정답 원천과 같다.
  - 설계 제약 준수: SWE-Shield의 충족률과 위반률. 12장 과제와 이어진다.
  - 해결률(시험 통과)은 모델의 수정 능력이 섞이므로 보조 지표로만 둔다.
- **비교 대상**: grep만 쓰는 에이전트, 벡터만, 그래프만, 이 시스템 전체, 그리고 가능하면 공개 구현이 있는 방법
  (LocAgent 등)을 같은 표본에 돌린다. 공개 구현이 Python 전용이면 그 한계를 적는다.
- **반복과 표본**: 논문들은 대부분 한 번 돌렸다. 여기서는 반복을 두고 흔들림을 함께 보고한다. 표본 수가 논문보다
  작으면 그 사실을 적고, 숫자를 직접 나란히 놓지 않는다.
- **필요한 준비**: 표본 선정 규칙, 기준 커밋별 색인, 정답 추출 스크립트(지금 있는 기계적 정답 추출을 함수, 파일,
  모듈 단위로 확장), 판정 스크립트, 비교 대상 실행 환경.
