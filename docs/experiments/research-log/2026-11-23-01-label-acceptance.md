# 2026-11-23 연구일지 01: core 라벨 수용과 다음 실험의 순서

세션: second-brain-eval-kit에서 연 Claude 세션. 작업 5를 마쳤다.

## 정한 것

- **라벨 검토는 Claude가 기준을 적용해 진행한다.** 사용자의 말이다. "라벨은 우선 너가 설정한 기준으로 진행해보고,
  이상하면 다시 검토하는것으로 할께. 11개를 지금 다 체크할수 없어." 그래서 이 라벨은 사람이 하나씩 수용한 라벨이 아니다.
  결과를 해석할 때 이 점을 밝힌다.
- **기준:** 시니어가 이 증상을 받으면 결국 원인으로 찾아내야 하는 곳이 core다. 수정 커밋이 바꿨더라도 정리 수정이나
  같은 규칙을 다른 곳에 적용한 수정은 related로 둔다.
- **로그 역추적 실험은 1단계 뒤에 별도로 한다.** 사용자가 추천 A를 골랐다. 1단계(결정 A, 실험 1)를 먼저 마치고,
  역할별 탐색과 로그 역추적은 새 문항 묶음과 새 그래프 정보로 따로 잰다.

## 라벨 결과

`data/oracle-accepted.json`에 적었다. `oracle-relayed.json`은 고치지 않았다. 실행기는 이제 accepted 파일을 읽는다.

| 문항 | 결정 | 이유 |
|---|---|---|
| sym-73 | `InjectContracts`를 related에서 core로 | 증상의 두 번째 부분(빈 초기 할당이면 패닉)을 고친 곳이다. 수정은 빈 할당을 만드는 코드를 `GetSystemContractsTransition` 호출 앞으로 옮겼다 |
| sym-55 | 유지 | `newRoundChangeTimer`, `handlePreprepareMsg`는 `timerMu` 잠금 2줄씩만 더했다 |
| sym-56 | 유지 | 같은 정리 함수를 `initialize*` 함수 모두에 적용했으므로 `initializeBase` 하나만 core인 것은 임의다. 다만 이 문항은 출발 심볼이 하나도 노드로 풀리지 않아 어느 쪽이든 비긴다 |
| 나머지 8문항 | 유지 | core 위치에 수정의 실제 로직이 있다 |

core는 19개에서 20개가 됐다.

## 알게 된 사실

- 1단계 11문항의 증상 문장에는 실제 로그나 에러 문자열이 하나도 없다(`data/questions-symptom.json`). 로그 역추적은
  이 문항으로 잴 수 없다.
- 그래프 노드 종류에 로그나 문자열을 담는 종류가 없다(`pkg/graph/types/enums.go`).
- 기준 커밋 `8d7930a4`의 비테스트 Go 코드에는 `log.Error` 등 로그 호출이 1,697곳, `errors.New`와 `fmt.Errorf`가
  2,578곳 있다(`git grep`).
- 같은 그래프에서 승격 메서드 노드는 726개다. 메서드 노드 8,133개의 8.9%이고, 모두 canonical id가 비어 있다.
