# 실제 로그로 하는 확인 실험

작성 2026-11-24. 시제품을 이 문항에 돌리기 전에 고정한다. 규칙은 [RULES.md](./RULES.md) 1판 그대로다(`trace.go`, `flow.go`, `graph.go`, `message.go`는 `6b5a569a`와 같다).

## 왜

앞의 문항은 diff를 본 에이전트가 문구를 적었다. 사용자가 go-stablenet의 수정 PR에서 에러 로그로 발견된 사례를 찾아 실험하라고 했다.
여기서는 이슈와 PR에 사람이 붙인 로그 줄을 그대로 쓴다.

## 자료

- go-stablenet(공개 저장소) 병합 PR 113개 중 수정 PR 67개와 댓글, 이슈 15개, 그 PR이 가리키는 go-ethereum PR과 이슈.
- 같은 저장소 커밋 기록의 2022~2024년 go-ethereum 수정 285개(Go 1.17 이상, 테스트 아닌 기존 Go 파일 1~5개)와 그 PR, 이슈.
- 합쳐 351개 수정에서, 경고 이상 로그나 오류 줄이 기준 커밋의 테스트 밖 문자열(10자 이상, 두 낱말 이상, 5줄 이하)과 맞는 것이 29개였다.

## 문항 고르기

- 로그 줄: INFO와 DEBUG를 뺀 맞는 줄 중 가장 심한 것(Fatal, panic, CRIT, ERROR, 오류 응답, WARN 순, 같으면 먼저 나온 것).
- 그 줄이 이슈나 PR이 문제로 지목한 것인지 Claude가 글만 읽고 정했다. 시제품의 출력은 보지 않았다.

| 처리 | 문항 |
|---|---|
| 확인에 씀 (13) | pr-92, pr-122, gh-25234, gh-25467, gh-25455, gh-25331, gh-26518, gh-26771, gh-26776, gh-27162, gh-27628, gh-28014, gh-28135 |
| 이미 본 문항이라 따로 적음 (8) | pr-83, pr-123, gh-25609, gh-25922, gh-26485, gh-26747, gh-28718, gh-28581 |
| 뺌: 줄이 문제 자체가 아님 (4) | gh-27479(문제는 패닉 스택), gh-27842(문제는 외부 패키지의 패닉), gh-28124(문제는 되감기), gh-25616(예제 코드) |
| 뺌: 로그를 더하는 수정 (1) | gh-28379 |
| 뺌: 노드 밖의 도구나 테스트 (3) | gh-28362, gh-28397, gh-28900 |

- 시제품 입력: 로그 줄에 들어 있는 기준 커밋 문자열 조각을 줄에 나온 순서대로 `: `로 이은 것. 값과 시각은 들어가지 않는다.
- 정답: 수정이 바꾼 테스트 밖 최상위 선언 전부(기준 커밋 그래프). 함수 안 선언은 그 함수로 센다. 사람이 고르지 않는다.
- 정답이 그래프에 하나도 없는 문항은 빼고 수를 적는다.
- 그래프: pr 문항은 앞에서 빌드한 것이 있으면 그것, 없으면 같은 방법. gh 문항은 빈 모듈 캐시로 고친 ckg로 빌드한다.

## 견주는 방식

- **tracer:** 시제품의 순위.
- **emit_file:** CONFIRM.md의 기준선.
- **interleave:** tracer 1위, emit_file 1위, tracer 2위, ... 순으로 섞고 같은 선언은 먼저 나온 것만 둔다. 앞 확인에서 둘이 찾은 문항이 겹치지 않은 것을 보고 정했다.

## 재는 값과 판정선

- 문항 값은 정답이 하나라도 10위 안에 들면 1, 아니면 0이다. 정답 recall@10과 첫 정답의 순위도 적는다.
- **주 판정:** interleave와 emit_file. 갈린 문항이 12개 이상이고 부호 검정 양측 p가 0.05보다 작아야 판정한다. 문항이 13개 이하라 판정이 나기 어렵다는 것을 안다.
- 함께 적음: tracer와 emit_file, tracer와 interleave, 이미 본 문항의 같은 값(판정에 쓰지 않음), 못 찾은 이유.

## 약점

- 문항을 고른 판단에 Claude가 들어갔다. 고른 이유를 위 표에 적었다.
- 정답에 정리 수정이 섞인다.
- 로그에 맞는 문자열이 있는 수정만 남는다. 패닉 스택만 있는 이슈는 빠진다.
