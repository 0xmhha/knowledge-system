# 결함의 관계를 따라 코드를 모아 주는 graph: 검토 보고서

작성 2026-11-24, 같은 날 고침(5장의 크기, 6장의 덱, 9장의 G0R 결과). 새 연구의 출발점이다. 제품 코드는 바꾸지 않았다. 숫자는 [data/summary.json](./data/summary.json)에 있고,
스크립트와 원자료는 저장소 밖 `knowledge-data/agent-eval/runs/20261124-defect-patterns`에 있다.

## 결론

방향은 타당하다. 다만 세 가지를 고쳐야 한다.

1. **조회를 둘로 나눈다.** 리팩토링은 한 방향으로 빠짐없이 펼치고, 결함은 정해 둔 관계만 골라 펼친다.
2. **패턴 28개를 규칙 28개로 만들지 않는다.** 관계 5종으로 접힌다(제품 결함 186건 중 153건, 작성자의 배정). 나머지 33건은 관계로 잡을 수 없다.
3. **결함 후보를 점수로 잘라 내지 않는다.** 빠진 이름을 정답에서 가져와도 10위 안은 11/34였다. graph는 모으고, 판단은 LLM이 한다.

graph가 LLM을 돕는다는 증거는 이 보고서에도 없다. 만들기 전에 여지부터 쟀다(9장). **리팩토링 쪽은 여지가 없었다**([HOPGATE-RESULT](./HOPGATE-RESULT.md)).

## 1. 무엇을 검토했나

출발은 사용자의 생각 네 가지다. 찾는 키워드가 원인이 아닌 때가 많다. 있어야 할 곳에 없어서 문제인 때가 있다.
문제에는 패턴이 있으므로 패턴에 관련된 코드를 주는 편이 낫다. 리팩토링에는 빠짐없는 연결과 hop별 확장이 맞다.

여기에 실행 방식이 하나 붙는다. DFS처럼 hop을 넓히며 노드의 body를 보고, 줄 정보를 queue에 넣어 정리해 한 번에 답한다.

| 주장 | 자료가 말하는 것 | 판정 |
|---|---|---|
| 키워드가 원인이 아닌 때가 많다 | 1단계 blind에서 core 20개 중 15개가 출발 심볼이 아니었다. 그러나 코드를 읽는 에이전트가 고른 2단계 15문항은 core가 모두 출발 심볼이었다 | 부분 지지. 첫 키워드는 자주 빗나가지만 LLM이 스스로 옮겨 간다 |
| 있어야 할 곳에 없다 | 결함 211건 중 111건이 빠뜨림. 정리한 59건 중 34건이 이미 있는 희귀한 이름을 새 함수에 들여왔다 | 빈도는 지지. 이름으로 그 자리를 짚는 것은 지지 안 됨(3장) |
| 패턴에 관련된 코드를 준다 | 관계 5종으로 접힌다. 관계마다 필요한 graph 이동이 다르다 | 설계로 타당. 효과는 재지 않았다 |
| 리팩토링은 빠짐없는 hop 확장 | 앞으로 2 hop은 300개 모두 1.6만 토큰 안이고, 뒤로 2 hop은 6개가 2만 토큰을 넘는다 | 실현 가능. 빠짐은 남아 있다(5장) |

## 3. "있어야 할 곳에 없다"를 재어 봤다

수정 전후의 코드를 파싱해, 바뀐 함수에 새로 들어온 이름이 저장소의 다른 곳에 이미 있었는지 셌다.
지역 변수, 매개변수, 시험 도우미, 기준 커밋이 어긋난 4건은 뺐다. 남은 113건이다.

| | 빠뜨림 59건 | 틀림 48건 |
|---|---|---|
| 함수 1~30개가 이미 쓰는 이름이 들어옴 | 34 | 22 |
| 흔한 이름(31개 이상)만 들어옴 | 4 | 7 |
| 처음 생긴 이름만 들어옴 | 3 | 1 |
| 들어온 이름 없음(조건, 순서, 값만 바뀜) | 12 | 12 |
| 기존 함수를 바꾸지 않음(설정, 컨트랙트, 새 파일 등) | 6 | 6 |

- **이름이 들어왔다고 그 이름이 원인은 아니다.** 거르기 전의 40건에서 12건을 무작위로 읽으니 핵심이 6, 부수적인 이름이 5, 판단 불가가 1이었다.
- **빠뜨림만의 특징이라고 말할 수 없다.** 틀림에서도 22/48이다. 큰 수정일수록 새 이름이 들어오기 쉽다. 함수 하나만 바꾼 빠뜨림은 13/27이다.

그 이름을 안다고 치고, 이름을 쓰는 함수들과 비슷한데 이름이 없는 함수를 앞에 놓아 봤다(저장소 함수 약 1만 1천 개).

| 빠뜨림 34건, 바뀐 함수의 순위 | 10위 안 | 50위 안 | 100위 안 | 중앙값 |
|---|---|---|---|---|
| 식별자 집합이 비슷한 순, 이름 중 최선 | 11 | 22 | 25 | 38.5 |
| 식별자 집합이 비슷한 순, 이름 중 중앙 | 4 | 15 | 20 | 66.3 |
| 같은 파일, 같은 패키지 순, 이름 중 최선 | 5 | 15 | 19 | 75.5 |
| 같은 파일, 같은 패키지 순, 이름 중 중앙 | 3 | 9 | 14 | 211 |

- "최선"은 정답을 보고 고른 값이라 상한이다. 한 가지 방법만 쟀으므로 다른 방법까지 안 된다고는 말할 수 없다.
- 희귀한 이름을 함께 쓰는 함수를 모두 모으면 29/34가 들어오지만, 모은 함수가 중앙값 516개다(최대 1,912개).
- 이 시험은 이름을 정답에서 가져왔다. 실제 조회에서는 이름도 모른다.

판단: 빈도는 크지만, **빠진 자리를 이름의 유사도로 짚는 기능을 먼저 만들 근거는 없다**. LLM이 이름을 정한 뒤 "이 이름을 다뤄야 할 형제는 어디인가"를 물을 때 답하는 쪽이 맞다.

## 4. 패턴을 관계로 접는다

28패턴마다 질의를 만들면 패턴 하나에 규칙 하나가 된다. 시험마다 기능을 쌓지 않는다는 규칙과 어긋나고, 앞 연구의 계열 규칙은 새 21문항에서 0건 맞았다.
그래서 "LLM이 심볼 하나를 쥐었을 때 어떤 코드를 나란히 봐야 판단이 되는가"로 접었다. 배정은 작성자 혼자 했고 이중 판정은 없다.

| 관계 | 나란히 볼 코드 | 건수(빠뜨림) | 여러 파일 수정 | graph 이동 |
|---|---|---|---|---|
| 값의 일생 | 이 값을 쓰는 곳, 갱신하는 곳, 순서 | 43 (18) | 26 | 함수 → 읽는 필드 → 그 필드를 쓰는 함수 |
| 호출의 양 끝 | 부르는 쪽의 가정, 불리는 쪽의 약속 | 36 (16) | 8 | 함수 ↔ 피호출자 body, 함수 ↔ 호출자 body |
| 형제 | 같은 것을 다루는 다른 자리, 그중 빠진 자리 | 30 (25) | 15 | 이름 → 쓰는 함수들, 그 집합의 차 |
| 입구의 검사 | 입구에서 여기까지의 길, 길 위의 조건 | 26 (22) | 14 | 함수 ← 호출자 … ← 입구, 길 위의 조건문 |
| 짝과 공유 | 얻기와 돌려주기, 같은 값을 만지는 다른 흐름 | 18 (14) | 5 | 함수 ↔ lock, channel, goroutine ↔ 다른 함수 |
| (관계 없음) | 식, 경계, 상수가 그 자리에서 틀림 | 33 (7) | 15 | 함수 자신의 body |

- 앞의 다섯이 153/186(82%)이다. 빌드와 시험 코드의 결함 25건은 뺐다.
- **결함을 종류로 맞힌 뒤 조회하는 방식은 쓰지 않는다.** 증상으로 계열을 맞히는 비율은 7월 이전 64/146이다(가장 많은 계열만 찍으면 25/146). 세 개까지 허용하면 114/146이지만, 증상 라벨은 수정을 본 작업자가 붙인 것이라 실제 조회에서는 더 낮을 수 있다.
- 대신 쥔 심볼에서 다섯 관계를 **모두 조금씩** 펼치거나 LLM이 관계를 고른다. 이것이 더 낫다는 측정은 없다.

## 5. hop별 확장의 크기와 빠짐

go-stablenet graph(노드 18.4만)에서 함수 300개를 뽑아 닿는 선언의 body 토큰(바이트/4)을 쟀다. 출발점은 결함과 무관한 무작위 함수다.

| 걷기 | 2 hop 중앙 / p95 / 최대 | 4 hop 중앙 / p95 / 최대 | 4 hop 2만 토큰 초과 |
|---|---|---|---|
| 호출, 앞으로만 | 380 / 5,058 / 12,338 | 1,025 / 17,391 / 69,617 | 12/300 |
| 호출, 뒤로만 | 738 / 5,647 / 14,434 | 2,696 / 15,850 / 103,579 | 12/300 |
| 호출과 값, 앞으로만 | 591 / 5,758 / 14,264 | 1,506 / 22,028 / 90,892 | 16/300 |
| 코드 간선 18종, 앞으로만 | 791 / 5,933 / 15,038 | 2,059 / 24,678 / 98,017 | 16/300 |

| 방향을 섞은 걷기 | 2 hop 중앙 / p90 | 3 hop 중앙 / p90 |
|---|---|---|
| 호출 | 7,628 / 91,902 | 56,218 / 270,643 |
| 코드 간선 18종 | 23,752 / 173,390 | 231,965 / 527,453 |
| 코드 간선 18종, 이웃 50개 넘는 노드에서 멈춤 | 8,348 / 34,367 | 33,519 / 118,224 |

- **위 표는 인터페이스에서 구현으로 가는 칸도 한 hop으로 센 값이다.** 호출만 세면(6장의 덱) 같은 hop에서 더 많이 닿는다. 아래 표가 바른 값이다.

| 호출, 바르게 센 hop | 2 hop 중앙 / p95 / 최대 / 2만 초과 | 4 hop 중앙 / p95 / 최대 / 2만 초과 |
|---|---|---|
| 앞으로만 | 544 / 7,060 / 15,222 / 0 | 1,359 / 29,438 / 84,407 / 24 |
| 뒤로만 | 1,024 / 8,981 / 54,036 / 6 | 2,962 / 33,306 / 132,908 / 41 |

- **앞으로 2 hop은 전부, 뒤로 2 hop은 300개 중 294개를 본문째 보낼 수 있다.** 넘는 부분은 서명만 보낸다.
- **섞으면 허브에서 멈춰도 3 hop에서 넘친다.** 그런데 결함의 정답은 섞어야 닿는다. 1단계 정답 15개 중 정방향 6 hop에 6개, 양방향 3 hop에 14개였다.
- **섞는 종류를 정하면 작아진다.** "읽는 필드 → 쓰는 함수"는 중앙값 246토큰(p90 4,776), "같은 호출자 → 다른 피호출자"는 534(5,539)다. "같은 피호출자 → 다른 호출자"는 3,303(95,385)이라 호출자 20개 상한을 두면 922(10,452)다.
- 조회를 둘로 나누자는 근거는 크기만이 아니다. 리팩토링은 빠짐이 비용이고 결함은 잡음이 비용이라 목적이 다르다(의견).

### 빠짐 없이는 지금 안 된다

| 빠지는 자리 | 확인한 값 |
|---|---|
| 패키지 수준 변수, 상수의 초기값에서 부르는 함수 | 함수 사용 목록 재현율 0.933, 빠진 154개 중 137개. graph에서 변수가 출발하는 calls 간선이 0개다 |
| 필드 사용 | 재현율 0.998, 정밀도 0.996 |
| 검토용 색인(`code_edges`) | `reads_field`와 `dispatches_to`가 들어 있지 않다 |
| 풀지 못한 참조, 읽지 못한 패키지 | 이 graph에서 20,721건, 31건 |
| reflection, 다른 빌드 태그, 생성 코드의 바깥 | graph가 원리상 못 본다 |

"누락 없음"은 약속할 수 없다. 대신 **응답마다 무엇을 다 봤고 무엇을 못 봤는지 적는 계산서**를 붙인다.
초기값 간선은 한 시험을 위한 기능이 아니라 graph의 정확성 결함이므로 고치는 것이 맞다고 본다(의견). 고치면 모든 문항 묶음에서 다시 잰다.

### 지금 도구가 모자란 점

- `find_callers`, `find_callees`는 호출 간선만 걷는다. `get_subgraph`는 모든 간선을 양방향으로 걷는다. 관계와 방향을 고를 수 없다.
- 응답의 노드에 몇 hop인지, 무엇을 거쳐 왔는지가 없다. 펼치지 않은 앞쪽(frontier) 목록도 없다.
- **`find_callers`와 `find_callees`가 hop을 다르게 센다.** 설명은 dispatch를 hop으로 세지 않는다고 하는데, 걷기 안에서는 한 칸으로 센다. 2 hop에서 앞쪽은 300개 중 59개, 뒤쪽은 77개 출발점이 닿아야 할 노드를 놓친다. 실제 도구를 45번 불러 흉내 낸 값과 같음을 확인했다(놓친 169개 모두 응답에 없음).
- depth 상한이 5다. 값에서 방향을 바꾸는 이동(필드를 읽고 그 필드를 쓰는 곳으로)이 걷기 안에 없다.
- 어느 함수가 락 없이 필드를 만지는지 바로 답할 수 없다. `accessed_under_lock`은 필드와 락을 잇고 함수가 빠져 있다. 함수의 락 얻기와 교차해 어림하면 필드 898개 중 683개가 섞인 것으로 나와 쓸 수 없다.

## 6. 제안하는 구조

```text
LLM이 쥔 심볼(또는 고친 diff) + 관계 + 방향
  1 seed      심볼을 노드로 푼다. 여럿이면 되묻는다
  2 expand    hop마다 관계별로 넓힌다. 방문 표시로 되풀이를 막는다
  3 read      노드 body에서 사실을 뽑는다 (판단하지 않는다)
  4 enqueue   관계, hop, 온 길, 사실, 토큰 크기를 덱에 넣는다
  5 pack      예산 안에서 본문, 서명, 이름 세 단계로 담는다. 버리지 않는다
  6 account   다 본 범위, 못 본 이유, 펼치지 않은 앞쪽을 적는다
```

### body에서 뽑는 사실

판단은 LLM이 하므로 서버는 사실만 뽑는다. 재료가 되는 문장 단위 간선은 이미 있다(뽑아 보지는 않았다).

- 조건과 그 조건이 읽는 값(`cond_reads`, `cond_calls`), 본문이 쓰는 값(`body_writes`).
- 얻고 돌려주는 락, 채널 송수신, 시작하는 goroutine.
- 에러를 만들거나 버리는 자리는 지금 간선이 없다. 1차에서 뺀다.

LLM을 서버 안에서 돌려 body를 거르는 방법도 있다. 비용과 비결정성이 생기고, 거르다 정답을 버려도 부르는 쪽이 모른다. 1차에서는 쓰지 않는다.

### 순회는 DFS 하나로 하지 않는다

| 순회 | 맞는 곳 | 안 맞는 곳 |
|---|---|---|
| BFS(hop 순서) | 리팩토링 목록. hop이 정의되고, 예산이 다하면 먼 것부터 줄어든다 | 길을 설명할 때 |
| DFS | 입구에서 여기까지의 길 나열. 길 단위로 조건을 모은다 | 예산이 있는 확장. 첫 가지로 깊이 들어가 예산을 다 쓰고, 간선 순서에 결과가 달린다 |
| 덱(0-1 BFS) | 무게가 0인 칸(인터페이스에서 구현으로)과 1인 칸이 섞인 걷기. 포장 순서 | 무게가 셋 이상으로 나뉠 때 |

그래서 리팩토링은 덱을 쓰는 0-1 BFS, 입구의 검사는 DFS, 포장은 hop별 묶음을 담은 덱을 쓴다. 점수로 맞춘 순위는 쓰지 않는다. 앞 연구에서 맞춘 순위는 새 자료에서 0.2561에서 0.110으로 떨어졌다.

### 덱을 쓰는 까닭 (사용자 제안, 2026-11-24)

처음에는 우선순위 queue를 적었다. 순서를 정하는 것이 관계, hop, 갈래 수뿐이라 힙이 필요 없고, 덱이 세 가지를 더 해 준다.

- **hop을 바로 센다.** 인터페이스에서 구현으로 가는 칸은 무게가 0이다. 무게 0은 앞에, 1은 뒤에 넣으면 덱 하나로 정확한 hop 순서가 나온다. 이렇게 걸은 호출 목록은 2 hop에서 앞쪽 5,294개(지금 도구 4,912개), 뒤쪽 2,675개(2,412개)다.
- **예산을 뒤에서 줄인다.** 가까운 hop은 앞에서 꺼내 담고, 예산이 넘으면 먼 hop을 뒤에서 꺼내 본문, 서명, 이름 순으로 낮춘다. 버리지 않는다.
- **앞뒤를 한 줄로 놓는다.** 부르는 쪽은 앞에, 불리는 쪽은 뒤에 붙이면 호출 순서대로 읽힌다.

한계도 있다. 같은 hop 안의 순서(갈래 수)는 묶음을 따로 정렬해야 한다. 관계가 여럿이면 덱 하나로는 한 관계가 앞을 차지하므로 관계마다 덱을 두고 번갈아 꺼낸다.
무게를 더 잘게 나누면 덱으로는 안 되고 힙이 필요하다.

### 두 조회

| | `expand`(리팩토링) | `relate`(결함) |
|---|---|---|
| 입력 | 심볼, 방향(앞, 뒤), hop, 바꾸는 종류(서명, 타입, 필드 뜻, 삭제) | 심볼 또는 diff, 관계(없으면 다섯 모두) |
| 걷기 | 한 방향, BFS. 바꾸는 종류가 걷는 간선을 정한다 | 관계마다 정한 이동 1~2번. 방향을 바꾸는 곳은 값, 호출자, 짝뿐 |
| 담는 순서 | hop 순서(덱의 앞에서) | 관계를 번갈아, 관계 안에서는 갈래가 적은 것부터 |
| 다르게 보이는 것 | hop별 묶음, 앞쪽 목록, 계산서 | 관계별 묶음, 대조표(형제 중 이 이름이 있는 곳과 없는 곳) |
| 실패의 뜻 | 빠짐 | 잡음 |

### 응답 모양(예)

```json
{"seed": "pkg.T.Method", "mode": "expand", "direction": "backward",
 "hops": [{"hop": 1, "nodes": [{"name": "pkg.Caller", "at": "a.go:10-42", "via": ["calls"], "from": "pkg.T.Method",
   "facts": {"conditions": ["12: if x == nil"], "writes": ["T.state"]}, "body": "..."}]}],
 "names_only": ["pkg2.Far a/b.go:7"],
 "frontier": [],
 "account": {"walked": ["calls", "invokes", "dispatches_to"], "complete_to_hop": 3,
   "not_seen": [{"why": "dispatch_by_type", "count": 2}, {"why": "package_initializers", "count": null}]}}
```

- **한 응답에 다 담는다.** 나눠 보내면 에이전트가 나머지를 가져가지 않았다(0/20, 0/6, 1/14). 11만 자 안팎은 정확히 읽었다(210/210). 예산 기본값은 2만 토큰을 제안한다(의견).
- **이름만이라도 모두 적는다.** 본문이 빠진 노드를 LLM이 보고 다시 물을 수 있어야 한다. 다시 묻는지는 재지 않았다.

### 쓰게 만드는 자리

도구를 놓아두는 것만으로는 쓰이지 않았다. 실제 결함 3문항에서 호출이 0번이었다. 그래서 LLM이 부르기를 기다리지 않고 **고칠 자리를 정한 시점에 붙여 주는 방식**을 같이 시험한다.
그 시점에는 심볼이나 diff가 있어 출발점 문제가 없다. 단점은 하네스를 바꿔야 하고, 필요 없는 문항에도 토큰을 쓴다는 것이다.

## 7. 남의 연구와 견주기

아래는 검색 결과 요약으로만 확인했고 원문 수치를 재현하지 않았다.

- **OrcaLoca**([arXiv 2502.00350](https://arxiv.org/abs/2502.00350v2)): 우선순위 queue로 다음 탐색을 정하고 함수마다 LLM이 관련도를 매긴다. 사용자의 queue 생각과 가장 가깝다. 관련도를 LLM이 매기는 점이 이 제안과 다르다.
- **LocAgent**([arXiv 2503.09089](https://arxiv.org/abs/2503.09089v2)): 코드 graph를 여러 hop으로 걷는 도구를 에이전트에게 준다. grep만 쓴 대조는 확인하지 못했다.
- **CoSIL**([arXiv 2503.22424](https://arxiv.org/html/2503.22424v1)): 미리 만든 graph 없이 탐색 중에 호출 graph를 만든다. 지금 하려는 것의 반대편 선택이다.
- **CodePlan**([arXiv 2309.12499](https://arxiv.org/abs/2309.12499)): 의존 분석과 변경 영향으로 고칠 자리를 줄 세운다. 저자 보고로 7개 저장소 중 5개가 검사를 통과했고 기준선은 0개였다. 리팩토링 쪽의 근거다.
- **Missing method call**([arXiv 1306.0762](https://arxiv.org/pdf/1306.0762)): 비슷한 쓰임의 다수에 있는 호출이 빠진 자리를 찾는다. 저자 보고로 오탐 5% 미만이다. 타입 쓰임이 많은 코드에서의 값이라 형제가 적은 합의 코드에 그대로 옮길 수 없다(의견).

## 8. 반박을 받고 고친 것

원자료와 결론 문장만 준 별도 에이전트에게 반박을 받았다.

| 반박 | 처리 |
|---|---|
| 새로 들어온 이름을 고른 뒤 "그 함수에 없다"고 말하는 것은 순환이다 | 수용. "키워드 검색은 그 함수를 원리상 못 준다"는 문장을 철회했다. 제목의 낱말이 바뀐 본문에 90/106 있다 |
| 줄 대응, 지역 변수, 이름 충돌, 기준 커밋 어긋남 | 수용. 수정 전후를 파싱해 다시 셌다(40/59에서 34/59, 순위 10위 안 최선 16/40에서 11/34) |
| 희귀 이름 공유 36/40과 396개는 짝이 아니다 | 수용. 짝을 맞춰 29/34와 중앙값 516개로 고쳤다 |
| "한 방향이면 전부 보낼 수 있다"는 꼬리를 뺐다 | 수용. 2 hop으로 좁히고 4 hop은 p95와 최대를 적었다 |
| 크기만으로는 조회를 나눌 근거가 못 된다 | 수용. 목적의 차이를 의견으로 적었다 |
| 증상 94/211에 확인용 65건이 섞였다 | 수용. 64/146으로 고쳤다 |
| 관계 목록이 분류기보다 낫다는 측정이 없다 | 수용. 측정이 없다고 적고 9장의 시험으로 보낸다 |

## 9. 다음 시험 (초안, 판정선은 실행 전에 커밋한다)

찾기는 grep 에이전트가 거의 다 풀었다(위치 8문항, 영향 범위 8문항). 그래서 **찾기가 아니라 "한 자리를 안 뒤 나머지를 빠짐없이 찾기"**를 잰다.
이 과제는 결함 수정과 리팩토링에 함께 걸린다. 실제 결함 5문항에서도 첫 자리는 5/5였고 나머지까지 다 찾은 것은 3/5였다(빠진 둘은 곁가지로 보이며 확인 안 됨).

| 단계 | 하는 일 | 결과별 행동 |
|---|---|---|
| G0 여지 | grep 에이전트에게 증상과 고친 자리 하나를 주고 나머지를 찾게 한다. 확인용 자료 중 여러 함수를 바꾼 16건에서 시드로 10건 | 재현율 0.8 미만이 4건 이상이면 G1. 아니면 결함 쪽을 접고 G0R만 |
| G0R 여지 | 인터페이스와 함수 값을 거치는 2~3 hop 변경의 영향 목록. 정답은 타입 검사기와 SSA. grep 에이전트 10문항 | F1 0.9 미만이거나 도구 결과 10만 자 초과가 4건 이상이면 `expand`를 만든다. 아니면 리팩토링 쪽을 접는다 |
| G1 오프라인 | `relate` 시제품의 2만 토큰 안에 나머지 자리가 드는가. 대조는 같은 파일, 호출 1 hop, grep | 세 대조를 모두 넘으면 G2. 아니면 멈춘다 |
| G2 에이전트 | 붙여 주는 방식과 grep을 같은 문항에서 여러 번 | 재현율을 지키며 토큰이나 호출이 줄거나, 재현율이 오르면 제품에 넣을지 정한다 |

- **정답을 둘이 따로 거른다.** 앞 시험에서 무승부 20문항 중 9개는 관계없는 수정이 한 커밋에 묶인 것이었다.
- **확인용이 적다.** 기준 커밋이 있는 제품 Go 결함 49건 중 여러 함수를 바꾼 것은 16건이다. 10건을 쓰면 6건이 남아 새 확인은 어렵다. 판정은 예비로만 읽는다.
- **앞 결과와 겹친다.** 함께 고친 곳 찾기는 이미 한 번 쟀고 같은 파일 방식(0.330)이 graph(0.180)와 grep(0.138)보다 나았다. 그때는 호출 중심 걷기였고 에이전트를 쓰지 않았다. 관계 이동은 이미 본 자료에서 떠올린 것이라 G1은 새 자료에서만 유효하다.

### G0R 결과 (2026-11-24)

10문항 모두 grep 에이전트의 F1이 1.000이었다. 읽은 결과가 10만 자를 넘은 것은 1개다. 사전 표에 따라 **리팩토링 쪽을 접는다**([HOPGATE-RESULT](./HOPGATE-RESULT.md)).
이 시험을 추천하며 "grep은 인터페이스를 거치는 호출을 이름으로 따라가기 어렵다"고 본 것은 틀렸다. 철회한다.

## 10. 위험과 단점

- **여지가 없을 수 있다.** 지금까지 graph를 붙여 정답이 오른 적이 없다. G0이 이것을 먼저 가른다.
- **관계 배정이 흔들린다.** 작성자 한 명의 배정이고, 패턴 라벨 자체가 모델이 붙인 것이다.
- **33건은 손대지 못한다.** 식이나 경계가 틀린 결함은 나란히 볼 코드가 없다.
- **저장소가 한 계열이다.** 세 저장소가 같은 원본에서 갈라졌고 결함 290건이 222단위로 겹친다.
- **계산서가 안심을 줄 수 있다.** `complete_to_hop`은 graph가 아는 간선 안에서의 완전함이다. 못 본 것의 개수를 모르는 항목은 null로 둔다.
