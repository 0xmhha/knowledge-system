# 여지 시험 G0R: 여러 hop 변경을 grep 에이전트가 풀 수 있는가

작성 2026-11-24. 사용자가 B(리팩토링부터)를 골랐다. 에이전트를 돌리기 전에 이 문서와 문항의 해시를 커밋한다.

## 1. 가를 결정

`expand`(한 방향, hop별, 빠짐을 적는 조회)를 만들 것인가. 앞 시험의 영향 범위 8문항은 hop이 하나였고 grep 에이전트의 F1이 0.984~1.000이었다.

## 2. 정답

[hopgold](./hopgold)가 Go 타입 검사기와 `refactor/satisfy`(어느 타입이 어느 인터페이스로 쓰이는지)로 만든다. 그래프는 읽지 않는다.

| 종류 | 변경 | 정답 |
|---|---|---|
| signature | 인터페이스 메서드에 인자가 하나 는다 | 같은 서명이어야 하는 메서드와 인터페이스를 더 늘지 않을 때까지 모으고, 그 가운데 하나라도 이름으로 쓰는 선언까지 |
| reach | 함수나 메서드의 동작이 바뀐다 | 3번 안에 그 함수에 닿는 함수, 메서드, 패키지 수준 변수. 인터페이스 메서드에서 구현으로 가는 것은 세지 않는다 |

두 번 만들어 sha256이 같았다. 빌드 범위의 패키지 134개 중 둘(cgo를 쓰는 잎 패키지)은 타입 검사에 실패했다. 그 패키지의 변환은 읽지 못했다.

## 3. 문항

go-stablenet 기준 커밋 `8f3774015d`. 아래를 모두 만족하는 것에서 시드 20261124로 종류마다 5개를 골랐다.

- 정답 10~60개, 파일 4개 이상, 정답에 빌드 밖의 메서드가 없다.
- 인터페이스를 빼면 정답이 20% 이상 준다(signature에서는 물은 메서드를 직접 쓰는 것만 센다).
- 변환으로 만든 정답과 메서드 집합만으로 만든 정답이 같다. 두 정의가 갈리는 애매한 문항을 막는다.
- 타입 검사에 실패한 패키지의 선언이 없다. 첫 추첨에서 이 조건이 빠져 문항 하나가 걸렸고, 에이전트를 돌리기 전에 조건을 더해 다시 골랐다.
- 패키지가 서로 다르고 정답이 절반 넘게 겹치지 않는다.

| 문항 | 정답(파일) | 인터페이스를 빼면 |
|---|---|---|
| s1 accounts.Wallet.Contains | 10 (5) | 1 |
| s2 gasprice.OracleBackend.ChainConfig | 40 (12) | 2 |
| s3 types.TxData.sigHash | 12 (7) | 6 |
| s4 snapshot.Iterator.Release | 15 (9) | 11 |
| s5 trie.node.cache | 13 (5) | 8 |
| r1 pebble.Database.Has | 59 (31) | 0 |
| r2 snapshot.diffStorageIterator.Slot | 28 (10) | 0 |
| r3 vm.accountManagerIsBlacklisted.Run | 11 (5) | 0 |
| r4 enr.IPv4.ENRKey | 54 (13) | 0 |
| r5 state.stateObject.SetBalance | 27 (16) | 18 |

해시는 [data/hopgate-freeze.json](./data/hopgate-freeze.json), 원자료는 저장소 밖 `knowledge-data/agent-eval/runs/20261124-hop-gate`에 있다.

## 4. 조건

- grep 조건 하나. 문항마다 새 에이전트 1개, 같은 모델, 반복 1회, 도구 호출 60번까지. 그래프는 주지 않는다.
- 채점은 파일, 수신자, 이름으로 선언을 찾는다. 물은 선언 자신은 뺀다.
- 명령이 소스 트리 밖을 열었는지, 금지한 명령을 썼는지 기록에서 본다. 어긴 문항은 빼고 이유를 적는다.

## 5. 판정 (실행 전에 고정)

문항 하나가 **어렵다**는 것은 F1이 0.9 미만이거나 읽은 도구 결과가 10만 자를 넘는 것이다.

| 결과 | 행동 |
|---|---|
| 어려운 문항이 4개 이상 | `expand` 시제품으로 간다. 두 기준을 나눠 적는다. F1로 어려운 것이 4개 미만이면 이득은 정확도가 아니라 읽는 양이라고 적는다 |
| 어려운 문항이 3개 이하 | 리팩토링 쪽을 접는다 |
| 채점할 수 있는 문항이 8개 미만 | 판정하지 않는다 |

- 에이전트의 답이 정답과 다른 곳은 코드를 읽어 정답의 잘못인지 본다. 정답이 틀렸으면 고치고 고치기 전과 후의 점수를 함께 적는다. 판정은 고친 점수로 한다.
- 보조(판정 없음): 같은 문항에서 그래프를 0-1 BFS로 걸은 목록과 지금 도구의 목록을 정답과 견준다. 에이전트는 쓰지 않는다.

## 6. 약점

- 문항이 인터페이스를 거치도록 골랐다. 보통의 변경이 얼마나 이런지는 말하지 못한다.
- signature는 컴파일러가 찾아 주는 변경이다. 빌드를 돌릴 수 있는 에이전트에게는 더 쉽다.
- 3번 안이라는 선은 임의로 정했다. 답의 크기를 다스리려고 둔 것이다.
- go-ethereum 원본과 겹치는 코드가 많아 모델이 기억할 수 있다.
