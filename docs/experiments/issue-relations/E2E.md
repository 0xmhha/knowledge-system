# 끝까지 고치기: 숨긴 테스트로 채점한다

작성 2026-11-24. 사용자가 A(실패부터 모으기)를 골랐다. 에이전트를 돌리기 전에 커밋한다.

## 1. 가를 결정

이 연구 줄을 이을 것인가. 여태의 시험은 자리를 찾는 일이었고 grep 에이전트가 거의 다 맞혔다([CRITIQUE](./CRITIQUE.md) 1장). 찾고 **고치는** 일에서 grep 에이전트가 어디서 틀리는지를 처음으로 모은다.

## 2. 쓸모없어지는 경우 (먼저 적는다)

- 실패가 적으면 "이 문항들에서 도울 자리가 없다"까지만 말한다. 문항이 쉬운 쪽일 수 있다(5장).
- 실패가 있어도 그래프가 메울 수 있다는 뜻은 아니다. 실패의 종류를 나눠 그다음에 고를 것을 정한다.

## 3. 문항

- 제품 Go 결함 수정이면서 테스트가 함께 들어온 45건(CRITIQUE의 55건은 조건이 다른 어림이었다). 2026-07-01 이후 만들어진 20건만 본다. 모델 지식 기준일이 2026-06이라 수정 자체를 외웠을 수 없다.
- 20건의 수정 커밋에서 테스트 파일을 가져와 기준 커밋에 얹었다. 기준에서 실패하고 수정에서 통과하는 것(F2P)과 둘 다 통과하는 것(P2P)을 확인했다.
- 기준에서 컴파일되며 F2P가 있는 것 12건(go-wemix 10, go-wbft 1, 그리고 새 오류 이름 하나를 쓰는 go-stablenet 1). 빠진 것: 테스트가 새 이름을 요구하는 것, F2P가 없는 것, 포트나 cgo 때문에 돌지 않는 것.
- 여러 파일을 고친 3건은 반드시 넣고, 나머지 9건에서 시드 20261124로 7건을 골랐다. 고른 10건을 두 번 더 돌려 F2P 71개(전부)가 같은 결과였다. P2P는 한 문항에서 22개 중 10개만 안정해 그것만 쓴다.
- 버그 보고서는 PR 글과 수정과 테스트를 본 별도 에이전트가 썼다. 관측과 기대 동작만 쓰고, 코드 이름, 파일, 원인은 쓰지 않는다. 고친 줄에 나오는 이름이 글에 있는지 기계로 확인했다(없음. RPC 이름과 에러 문구 일부만 겹친다). 테스트가 새 이름을 요구하는 1건은 그 이름과 쓰임을 따로 준다.
- 글, 정답, PR 번호는 저장소 밖에 둔다.

## 4. 조건과 채점

- 문항마다 새 에이전트 2개, 같은 모델, grep 도구만(rg, grep, sed 등). 자기 복사본에서 고치고 기존 테스트와 자기 테스트를 돌릴 수 있다. git과 네트워크는 쓰지 않는다. 도구 80번까지.
- 채점: 에이전트가 고친 트리에 수정 커밋의 테스트 파일을 덮어쓰고 해당 패키지를 돌린다. F2P가 모두 통과하고 안정한 P2P가 깨지지 않으면 성공이다.
- 두 번의 결과가 갈리면 세 번째를 돌려 다수로 정한다.
- 실패한 실행마다 별도 에이전트가 트리 차이와 테스트를 보고 나눈다: **찾지 못함**(고쳐야 할 함수를 한 번도 보지 않음), **판단 틀림**(보고 잘못 고침), **불완전**(일부만 고침), **환경**(시간, 도구 한도, 빌드), **테스트가 좁음**(동작은 맞는데 숨긴 테스트가 구현을 요구). 마지막은 실패로 세지 않는다. 나는 나눔을 읽고 확인만 한다.
- 보조: 토큰(마지막 문맥, 더한 값), 도구 호출, 걸린 시간, 고친 함수가 기존 정답 함수를 얼마나 덮는지.

| 3개 이상이고 어느 쪽도 절반이 아님 | 종류를 나눠 보고하고 정하지 않는다 |

## 6. 약점

- 문항이 작다(10개). 10개 중 7개는 더한 줄이 20줄 이하다. 여러 함수를 고친 문항은 3개다.
- go-wemix 8, go-wbft 1, go-stablenet 1이다. 세 저장소는 같은 뿌리다.
- 정답을 아는 에이전트가 증상을 썼다. 운영자가 실제로 올린 글은 더 모호할 것이다. 그래서 성공률은 실제보다 높을 쪽이다.
- 숨긴 테스트는 좁을 수 있고, 동작이 맞아도 실패할 수 있다.
- 결함의 절반 이상은 앞 시험의 위치 찾기 문항에서 본 단위일 수 있다. 에이전트는 새로 시작하므로 모델 쪽 기억은 없다.
