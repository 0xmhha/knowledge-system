# reach의 비용: grep, gopls, walk

작성 2026-11-24. 사용자가 A(이득 확인)를 골랐다. 에이전트를 돌리기 전에 커밋한다.

## 1. 가를 결정

[FORKONLY-RESULT](./FORKONLY-RESULT.md)에서 reach 12문항 중 11개가 `walk`를 주었을 때 토큰이 줄었다(문항마다 한 번, 모은 값은 사후). 이 이득이 되풀이되는가, 그리고 그래프여야 하는가.

## 2. 이 시험이 쓸모없어지는 경우 (먼저 적는다)

- 이득이 있어도 F1이 모두 1이면 정확도가 아니라 비용의 이득이다. 그것만 말한다.
- gopls 한 단계 조회로 비슷하게 줄면, 그래프 DB가 아니라 "이름이 풀린 조회"가 이득의 이유다.
- 여러 단계 걷기가 이유라 해도 gopls 위에 같은 걷기를 얹을 수 있다. 그래서 그 목록과 걸리는 시간을 에이전트 없이 따로 잰다(5장).

## 3. 조건

| 조건 | 검색 도구 |
|---|---|
| grep | rg, grep, find, sed, awk |
| gp | gopls v0.23.0을 감싼 도구. `grep`, `refs`, `callers`, `callees`(모두 한 단계) |
| gk | 그래프. `grep`, `refs`, `walk`(여러 단계). 앞 시험과 같은 파일(해시 같음) |

- `gp`와 `gk`는 출력 모양이 같고(`파일:줄 [감싸는 선언]: 코드`), 테스트와 주석을 뺀다. 읽기는 셋 다 sed 등이다. gp와 gk에서는 rg와 grep 검색을 막는다.
- gopls는 Go 팀의 공식 모듈이며 체크섬을 검증해 임시 폴더에 설치했다. 샌드박스 안에서 한 번에 1~6초가 걸린다. `gp refs`는 표본 40개 중 39개에서 타입 검사기의 사용 줄을 모두 냈다(1개는 이름을 못 찾음). 문항에 맞춘 규칙은 없다.

- 답은 JSON을 파일로 한 번 쓰고 `done`만 답한다(세 조건 같음). 앞 시험은 JSON을 바로 답했으므로 앞 시험의 토큰과 바로 견주지 않는다.
- 동시에 18개씩 묶어 돌린다. 한 묶음에 세 조건을 같은 수로 섞는다.

## 4. 문항과 판정

- 새 reach 문항 8개, 시드 20261129. 정답 10~60, 파일 4개 이상, 두 정의 일치, 패키지가 서로 다르고 앞 문항과 절반 넘게 겹치지 않는다. 4개는 인터페이스를 빼면 정답이 20% 이상 주는 것(`i`), 4개는 그렇지 않은 것(`p`, 보통의 경우).
- 문항마다 조건마다 3번(72번). 값은 세 번의 중앙값이다. 토큰은 마지막 메시지의 문맥 크기다. 보조로 메시지마다 더한 합, 메시지 수, 걸린 시간.

| 결과 | 말할 수 있는 것 |
|---|---|
| gk/grep 비의 중앙값 0.93 이하, 8문항 중 7개 이상에서 작고, F1 평균이 0.02 넘게 낮지 않다 | `walk`의 이득이 되풀이된다 |
| 그 밖 | 되풀이되지 않는다. 앞 12문항의 값은 보탬이 되지 않는 것으로 둔다 |
| gk/gp 비의 중앙값 0.95 이하, 8문항 중 6개 이상에서 작다 | 여러 단계 걷기가 gopls 한 단계 조회보다 낫다 |
| gp/grep이 gk/grep보다 0.03 안으로 같거나 낮다 | gopls로 충분하다 |

## 5. 에이전트 없이 재는 것 (판정 없음)

같은 8문항에서 gopls를 여러 번 불러 3단계를 걸은 목록과 `gk walk`의 목록을 정답과 견주고, 걸린 시간을 적는다.

## 6. 약점

- 저장소와 모델이 하나다. 질문에 걷는 법이 적혀 있다.
- gp와 gk는 rg를 막아 쓰게 했다. 실제로 스스로 쓸지는 재지 않는다.
- gopls 조회가 느려 시간 비교는 장비에 달렸다. 여러 에이전트가 함께 돌아 더 느려진다.
