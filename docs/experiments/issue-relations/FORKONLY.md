# go-stablenet에만 있는 코드에서 다시 견주기

작성 2026-11-24. 사용자가 "go-stablenet에만 있는 코드는 모델이 모른다. 그래서 앞처럼 동작할 수 없다"고 보고 다시 시험하자고 했다.
"이러한 문구로"는 이 전제를 조건으로 두는 것으로 읽었다. 두 조건의 프롬프트 모두에 "이 코드는 이 프로젝트에만 있으니 다른 프로젝트와 같다고 가정하지 말라"는 문장을 넣는다.
에이전트를 돌리기 전에 커밋한다.

## 1. 전제 확인 (P0)

- **fork 전용의 뜻:** 파일이 go-ethereum v1.13.15에 없고, 이름이 그 트리의 식별자(16,891개)에 하나도 없는 선언. 선언 13,263개 중 그 이름이 없는 것은 1,286개다.
- **약점:** 합의 코드(WBFT)는 다른 공개 프로젝트의 QBFT에서 왔다. go-ethereum에 없다고 모델이 모른다고 할 수 없다.
- **도구 없이 묻기:** fork 전용 함수 20개와 원본 함수 20개를 섞어, 부르는 함수의 이름을 도구 없이 쓰게 한다(2번). 정답은 타입 검사기. 묶음마다 재현율을 적는다.
- **읽는 법:** 원본의 재현율이 fork 전용보다 0.2 이상 높으면 전제를 지지한다. 둘 다 0.1 아래면 "이 정도 세부는 원본도 외우지 않는다"이고 전제를 가르지 못한다.

## 2. 여러 hop 문항 (P1)

- 앞의 조건(정답 10~60, 파일 4개 이상, 인터페이스로 20% 이상, 두 정의 일치)에 더해 시작 선언이 fork 전용 파일에 있고, 정답의 절반 이상이 fork 전용. 시드 20261126으로 signature 2, reach 4.
- 조건 둘: `grep`, `gk`(`grep`, `refs`, `walk`). `gk`는 앞 시험과 같은 파일(해시 같음). 조건마다 1번.
- **우월/열등:** GREPLIKE 5장과 같다(F1 차 0.02, 토큰 비 중앙값 0.95, 5/6).

## 3. 결함 (P2)

- 초기 21문항 평가의 문항 중 원인이 fork 전용 코드에 있고 계열이 다른 3개: 최소 팁 갱신(값의 일생), 합의 타이머(동시성), 설정 문자열(입력). 증상 문장은 앞에서 쓴 것 그대로이고 식별자가 없다. 정답은 수용한 core 라벨(2, 2, 1개)이다.
- 최소 팁 문항은 앞 평가(Sonnet)에서 grep 조건 0.55로 어려웠던 문항이다.
- 조건 둘, 조건마다 3번. 답은 5개까지. 문항마다 core 재현율을 잰다.

| 결과 | 말할 수 있는 것 |
|---|---|
| gk의 재현율 평균이 grep보다 0.3 이상 높다(9번 대 9번) | 이 문항들에서 gk가 정확도로 앞설 가능성이 높다 |
| 0.3 이상 낮다 | 해로울 가능성이 높다 |
| 그 사이이고, 토큰 비(문항별 중앙값의 중앙값)가 0.9 이하 | 정확도는 가르지 못하고 gk가 싸다 |
| 그 밖 | 차이를 말하지 않는다 |

## 4. 약점

- P2의 문항은 공개 저장소의 2026년 2~5월 수정이라 모델의 지식 기준일(2026-06) 앞이다. 모델이 수정을 보았을 수 있다.
- P2의 문항은 앞 연구에서 본 것이다. `gk`를 이 문항에 맞춘 적은 없다.
- 프롬프트의 새 문장이 두 조건의 행동을 함께 바꿀 수 있다. 앞 시험과 수를 바로 견주지 않는다.
- P1은 조건마다 1번이다. 모델 하나다.
