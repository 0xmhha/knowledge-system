## 2. 왜 이 작업을 시작했는가

출발점에는 이미 CKG 코드 구조·이력, CKV 코드/문서 검색, CKS 근거 팩이 있었다. 그러나 **비슷한 문장이나 코드 경로를 찾는 것과, 요구사항을 만족하는 구현을 근거로 설명하는 것 사이에 차이가 있었다.** 초기 분석은 데이터베이스 제품 교체보다 관계의 의미·출처·검증·버전을 명시하는 일을 제안했다.

당시 자체 CKG 색인은 현재 Go877파일을 모두 포함했지만 audit는 과거 Hunk에만 있는1,056경로를 현재 파일로 잘못 집계했다. 일반 필터의 전체KNN→3배 후보→후필터에는 제한적인 조건의 관련 결과 누락 가능성이 있었고, 긴 Markdown 뒷부분 절단과 답 없음 평가의 점수 특례도 발견했다. **감사 오집계는 당시 실측 재현, 검색 품질 영향은 당시 미측정**이므로 같은 확도의 사실로 취급하지 않는다.

그래서 첫 단계는 검색·인용·감사의 정확성을 확보하는 것이었다. 이후 코드가 보여 주는 구현, 문서의 설명, 스펙이 의도하는 동작, 특정 테스트 실행 결과를 같은 프로젝트·스냅샷·원문 위치에 묶고, 충돌·누락·미확인을 드러낸다. 관계 수를 늘리는 것이 아니라 **어떤 요구를 어떤 코드·테스트가 뒷받침하며 어느 버전에 유효한지**를 추적하는 것이 목적이다.

작은 온톨로지는 이를 위한 공유 의미 계약이다. 정의·포함/제외 범위·다국어 별칭·관계 방향/타입·근거를 관리하면서 미등록/모호한 용어 때문에 원래 자연어 검색을 잃지 않는다. 파일 원본과 파생DB, 공통core와 프로젝트 지식, 구조와 정책, 제안과 검증 사실을 구분한다. 초기 안은 모든 의미 객체를 CKG AST enum에 넣거나 RDF/OWL/GraphRAG를 한꺼번에 도입하는 계획이 아니다.

최종 사용 흐름은 임의 프로젝트에 설치하는 CKS와 **요구→근거 검색→추적/충돌 보고→변경 계획→외부 패치→테스트·사람 수용→동일 버전 재색인**이다. CKS 자체의 자율 코드 수정은 초기 범위 밖이다. 코드나 테스트 성공만으로 스펙 충족을 자동 승인하지 않는다.

## 3. 초기 계획에서 v2로 유지·구체화한 내용

초기는 정확성→검색→근거→온톨로지→개발 루프→설치형의 Gate0–5/W0–W5다. v2는 **D설계→A모델 독립 개발/구조 게이트→B실모델 평가→C평가 후 수정/판정**으로 실행 순서와 완료 조건을 재편했다. FR10/INV7/NFR5/S9를 유지하면서 모델 바이트, 안정 project/snapshot/dataset ID, 원문 보관, 비Git, pack lock, 정책/ADR, 외부 패치 수용 등을 R2로 구체화했다.

v2는 초기 목적을 대체하지 않는다. 현재의 품질fail·소표본inconclusive·ontology disabled·운영release withheld는 효과가 입증되지 않으면 기본 비활성으로 둔다는 초기 게이트에도 부합한다. 시험preview 종료를 검색 품질 개선·실제 파일럿 승인·운영 출시 달성으로 해석하지 않는다.
