# 소스 스냅샷과 인용 신원 계약

현재 구현은 internal/setup의 capture/identity/history 검증과 internal/system/evidencev2의 보관본 인용을 기준으로 한다. 초기 worktree 실험은 현재 빌드 경로가 아니다.

## 문제

현재 `cks setup`은 깨끗한 `committed` 입력만 받아 Git HEAD를 CKG/CKV 인용에 기록한다. 이는 안전한 제한이다. 더러운 작업 트리를 그대로 읽으면 두 엔진이 서로 다른 시점의 파일을 볼 수 있고, 같은 HEAD의 수정·신규 파일은 같은 버전으로 오인된다. Git이 없는 프로젝트는 지금 설치 경로에서 제외된다. 현재 CKV 매니페스트에는 안정 `project_id`/`dataset_id`/`snapshot_id`가 없으며 의미 투영은 자체 프로젝트/데이터셋 ID를 갖는다. 기존 인용 소비자는 커밋·경로·줄을 사용한다.

## 결정할 계약

| 좌표 | 정의 | 필수 불변식 |
|---|---|---|
| `project_id` | 한 번 발급하거나 명시해 설정에 보존하는 안정 ID. 이름·로컬 절대 경로와 별개 | 같은 ID를 다른 프로젝트에 재사용하면 거부. 이동/복제 뒤에도 ID 유지. |
| `source_commit` | 캡처 시작의 전체 HEAD SHA | Git 이력의 기준점이며 작업 트리 바이트의 유일한 신원이 아니다. |
| `file_manifest_digest` | 선별된 저장소 상대 POSIX 경로, 파일 종류, SHA-256, 실행 비트와 제외 정책 버전을 순서대로 직렬화한 SHA-256 | 수정·신규 파일·실행 비트·정책 변경으로 값이 바뀐다. 정렬/정규화/UTF-8 경로 규칙은 골든으로 고정. 구 v2 매니페스트는 기존 해시를 유지. |
| `snapshot_id` | `project_id`, `source_mode`, `source_commit`, `file_manifest_digest`, 캡처·Git 이력·파일 모드 정책을 버전별 도메인 분리 형식으로 해시 | 같은 HEAD의 다른 바이트·복구 이력·실행 비트가 신규 스냅샷에서 같은 ID가 될 수 없다. 구 v2–v4는 원래 계약대로 읽는다. |
| `dataset_id` | `snapshot_id`, 빌드 전 고정한 그래프/벡터/의미 입력 파일·정책 다이제스트 및 스키마, 임베딩 정체성을 해시. 출력 다이제스트는 제외 | 같은 원천의 다른 모델/정책/스키마는 다른 데이터셋. 순환 신원 없이 빌드 전에 계산되며 사용자 버전 별칭과 다르다. |

`committed`, `working-tree`, 비Git `snapshot-only`는 서로 다른 `source_mode`를 갖는다. 청결한 HEAD를 작업 트리 모드로 캡처해도 원문 파일 집합은 같지만 모드는 다른 신원이며, 검색 결과의 내용과 줄은 일치해야 한다. V1 인용의 `commit_hash` 필드는 계속 유지하고 새 v2 인용은 `snapshot_id`, `file_sha256`, `content_sha256`, `project_id`, `dataset_id`, `origin_id`를 필수로 가진다. **working-tree와 snapshot-only 인용의 `commit_hash`는 빈 문자열**이고 Git이 있을 때만 `base_commit`을 별도 필드로 기록한다. 구 소비자가 HEAD 원문으로 오해하지 않게 기존 MCP 인용 도구는 두 모드에서 `requires_v2`를 반환하고 새 v2 도구만 본문을 제공한다.

## 캡처와 승격 절차

1. 소스 루트의 실경로와 Git 공통 디렉터리를 확인한다. CKG/CKV가 실제 선택할 수 있는 원본 파일 경로 목록을 각 엔진의 탐지 규칙으로 계산한다. 정책이 다른 항목은 목록에 포함한 뒤 엔진별 예상 입력 여부를 표시한다. 비밀 경로, 모든 심볼릭 링크, 디바이스/소켓, 읽기 불가 파일은 명시적으로 제외하거나 오류로 처리하며 `doctor`에 개수만 노출한다. 경로 성분별 no-follow 열기로 검사한다.
2. 파일 목록과 각 원문 SHA-256을 읽고 후보의 별도 staging 디렉터리에 저장한다. 복사 직후 원본/사본의 크기·해시를 확인한다. 하드링크는 원본의 추후 쓰기로 바뀔 수 있으므로 사용하지 않는다. staging 위치는 활성 데이터셋 밖이다. 파일 권한은 빌더에 필요한 읽기만 남긴다.
3. Git 입력은 CKG의 이력 경로가 staged 바이트와 동일한 기준 HEAD를 볼 수 있도록 캡처한 history.bundle을 독립 Git 저장소로 복원하고 작업 트리 모드의 바이트/실행 비트를 오버레이한다. 공유 worktree의 이후 개발 이력을 읽지 않는다. 비Git 입력은 일반 staging 디렉터리를 쓰고 이력 패스를 끈다. 빌드는 staging만 읽고 원본 작업 트리를 읽지 않는다. 엔진에는 `build_root`와 `logical_source_root`(설정에 저장한 프로젝트 위치), `snapshot_id`를 별도로 전달한다. 경로 정렬·인용은 origin 상대 경로를 쓰고, 공개 매니페스트에 임시 `build_root`를 남기지 않는다. CKV/CKG의 `canonical_id`도 임시 위치에 종속되지 않아야 한다. 해당 불변식이 테스트에서 깨지면 모드를 출시하지 않고 캡처 어댑터를 고친다.
4. CKV/CKG와 의미 투영의 실제 원본 입력 경로/해시를 사전 목록과 대조한다. CKV가 읽는 생성 의미 텍스트는 별도 파생 매니페스트와 대조한다. 원본 작업 트리는 캡처 완료 후 바뀌어도 **캡처한 후보의 내용은 바뀌지 않는다**. 단, 캡처 도중 바뀐 파일은 실패시킨다. 후보의 저장 바이트와 각 출력 매니페스트를 빌드 종료 후 다시 검증한다.
5. 커밋/작업 트리 모두 원문 파일을 콘텐츠 주소로 후보에 보관한다. 근거 검증 API는 보관본을 기본 원천으로 사용하고 원본 저장소가 없어도 같은 상대 경로·줄 범위·SHA-256 계약을 제공한다. 과거 인용을 현재 소스 경로나 Git HEAD의 파일로 재해석하지 않는다. 보관본이 없거나 해시가 다르면 `source_missing`/`snapshot_mismatch`를 반환한다. 공간 회수는 인용 보존 정책과 함께 별도 명령으로 수행하고 활성/롤백 가능 버전의 원문은 지우지 않는다.
6. 그래프·벡터·의미 매니페스트의 모든 ID, 실제 파일 목록, 모델 신원을 검사한 후에만 `current`를 원자 전환한다. 실패/취소/프로세스 종료 중에는 이전 `current`와 그 원문 보관본을 유지한다. 승격 직후 질의/롤백도 같은 좌표를 재검증한다.

## 기존 데이터와 이전

기존 `committed` 데이터셋의 빈 `project_id`/`snapshot_id`는 `legacy_unpinned`으로 읽고 원래 커밋 인용만 제공한다. 다른 프로젝트/작업 트리와 결합하거나 의미 승격할 때 자동 보충하지 않는다. 사용자는 새 `cks init` 설정과 전체 재색인으로 v2 ID를 얻는다. 마이그레이션은 옛 DB 파일을 제자리에서 재해석하지 않는다. 새/옛 EvidencePack의 JSON 골든과 소비자 회귀가 통과해야 새 필드를 공개한다.

## 기술 검증과 실패 오라클

| 실험 | 통과 조건 |
|---|---|
| 같은 HEAD에서 추적 파일 수정→신규 파일 추가→다시 수정 | 세 `file_manifest_digest`/`snapshot_id`가 다르고 각 원문 인용이 보관본의 해당 바이트/줄을 가리킨다. |
| Git이 없는 코드·문서 디렉터리 | `snapshot-only`에서 AST/CKV/인용이 동작하고 커밋·blame은 비활성 상태로 표시한다. 파일 변경은 새 스냅샷이다. |
| 캡처 중 파일 변경·삭제·심볼릭 링크 교체 | 캡처 또는 해시 재검증이 실패하고 `current` 불변. |
| CKG 이력 포함 작은 Git 픽스처 | staged AST는 수정 바이트를 인덱싱하지만 이력 기준은 원래 HEAD이고 임시 절대 경로가 공개 팩에 새지 않는다. |
| 후보 그래프 성공/벡터 실패·의미 불일치·모델 교체 | 승격 거부, 기존 핸들/롤백 가능 버전 유지. |
| 동일 이름 두 저장소와 동일 commit SHA 테스트 데이터 | `project_id`가 다르면 조인/질의/캐시 키 분리. |
| 보관본 손상/삭제, 구버전 매니페스트 | 조용한 HEAD 재해석 금지. 명시 오류 또는 제한된 legacy 읽기. |
| 외부로 나가는 링크/비밀 경로/권한 실패 | 경로·원문 누출 없이 거부 또는 기록된 제외. |

## Git 복구 이력 봉인

CKG는 HEAD 도달 이력에 더해 reflog/fsck에서 최대 100개의 복구 커밋을 그래프에 넣는다. 공유 `git worktree`는 개발 저장소의 이후 이력을 읽을 수 있으므로 신규 Git 소스의 `snapshot_id` v4는 파일·HEAD·캡처 정책·선택된 복구 SHA 집합과 **Git 아카이브 정책**을 포함한다. v2/v3의 신원 계산과 보관본 읽기는 유지한다.

신규 캡처는 `sources/history.bundle`에 기준 HEAD와 선택된 복구 커밋의 Git 객체를 저장하고, `sources/manifest.json`에 bundle SHA-256·바이트 수·정렬된 복구 SHA를 기록한다. 캡처 시에만 원본 객체를 임시 bare 저장소의 alternate로 읽는다. bundle 출력은 기본 1 GiB(설치 시 `--max-git-history-bytes`로 조정)까지 스트리밍하며 초과·객체 누락·복구 집합 변경은 후보를 실패시킨다. 빌드는 bundle을 **독립 Git 저장소**에 복원해 캡처 파일을 덮어쓴 뒤 실행한다. 복원 저장소의 reflog/fsck가 선택된 SHA만 반환하는지 확인하고 alternate는 설치하지 않는다. 승격/보관본 검증은 bundle의 크기·해시와 v4 정책을 검사한다. 원본 저장소가 삭제되거나 GC된 뒤에도 보관본만으로 같은 입력을 재생할 수 있다.

CKG의 `graph_digest`는 코드 노드/엣지의 다이제스트이며 복구용 Commit/Hunk 노드·엣지는 제외한다. 따라서 B0-H 재현 시험은 `graph_digest`에 더해 AMBIGUOUS 복구 노드 ID 집합과 총 노드·엣지 수를 비교한다. 작은 Go 픽스처에서 원본 저장소 삭제 전후 CKG 빌드가 이 네 항목에서 일치했다. 큰 저장소의 아카이브 시간·크기와 macOS/Linux 간 재생 비용은 별도 측정 대상이며 실모델 품질 수치는 아니다.

## 실행 비트의 신원과 재생

실행 파일 30개가 있는 고정 코퍼스의 첫 v4 빌드에서 파일 바이트를 다시 쓰자 Git checkout의 실행 비트가 사라졌다. CKG/CKV 출력은 생성됐으나 승격 게이트의 Git clean 검사에서 거부됐다. 신규 캡처는 파일별 실행 비트와 `file_mode_policy=executable-bit-v1`을 기록한다. 파일 매니페스트 v3·스냅샷 v5에 이 값을 넣어 같은 바이트의 실행 비트 변경도 다른 신원으로 만든다. `committed` 빌드는 bundle에서 복원한 Git checkout을 그대로 사용해 HEAD에 포함된 모드를 유지하고, `working-tree`는 캡처한 실행 비트를 임시 파일에 재현한다. 캡처 전후 모드가 변하면 실패한다. 구 v2–v4 보관본은 기존 신원 방식으로만 읽고 재해석하지 않는다. 당시 검증은 원장의 기록된 증거에서 확인한다. [증거 복구](./EVIDENCE-RECOVERY.md)를 따른다.
