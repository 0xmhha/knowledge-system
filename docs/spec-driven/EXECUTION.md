### A1 bounded-search continuation (2026-10-01)

`sqlitevec.SearchDetailed` now records `complete|incomplete|cancelled`, a stable reason, the SQL candidate superset count, the number examined and—after exact scan—the true eligible count. The exact fallback has a default ceiling of 16,384 SQL candidates; a caller can lower it through `SearchOptions.MaxExactCandidates`. A short vec0 result above that ceiling returns `incomplete/candidate_limit` with its partial hits distinguished from a complete top-K result. The legacy `Search` API discards those partial hits and returns `ErrSearchIncomplete`; expired or cancelled contexts are not empty successes. If an unfiltered search returns fewer than K while more metadata rows exist, it reports `index_underfilled` rather than pretending the index is complete. The ceiling is a structural resource bound, not a measured latency or recall target.

The store also caps requested vector K at 16,384 and the query pipeline rejects a primary K that would exceed this bound after its 3× overfetch, including `dry_run`. The CLI and both MCP search handlers expose an oversized request as `code=incomplete` instead of converting a huge floating-point K to a negative integer and silently running the default K. Tests cover the store, the overfetch boundary, dry run and the legacy handlers.

The earlier "large fallback" fixture was corrected: its exact path prefix had actually reduced the SQL candidate set to one. The new bracket-glob fixture keeps 2,050 SQL candidates, forces ANN underfill, verifies the bounded failure, then verifies the default exact fallback finds the target. Empty and contradictory filters remain complete zero-hit results. Existing MCP success JSON remains unchanged; legacy CLI and MCP errors now carry `code=incomplete` or `code=cancelled`, and tests confirm the error cause remains recognizable. The v2 structured response is still A7.1 work.
