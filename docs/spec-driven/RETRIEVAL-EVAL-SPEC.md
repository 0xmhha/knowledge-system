# 정답이 있는 검색 평가 명세

상태: 사용자 승인(2026-10-23, 원문 "1. 명세대로 진행. 2. 한국어로"). 표본 규칙은 이 승인으로 고정하며, 결과를 본 뒤 바꾸지 않는다. 결정 근거는 [검색 평가 우선 결정](./operational-preparation/retrieval-priority-2026-10-23/DECISION.json)이다.

## 1. 목적

이 시스템은 어떤 프로젝트든 지식 DB로 만들어 두고, vibe query에 찾는 코드를 거의 한 번에 돌려줘야 한다. 이 평가는 그것을 두 가지로 나눠 잰다.

1. **의도 파악**: CKS가 질문의 의도를 맞게 분류하는가
2. **관련 코드 제공**: 정답 코드를 첫 번째 또는 앞쪽에 돌려주는가, 같은 변경에 묶인 다른 코드도 함께 주는가, 그때 얼마나 적은 토큰을 쓰는가

정답은 사람이 새로 만들지 않는다. 실제로 머지된 PR이 이미 정답을 갖고 있다. PR의 종류 라벨이 의도 정답이고, PR이 바꾼 함수가 코드 정답이다.

대상은 [grpc-go](https://github.com/grpc/grpc-go)이고, 같은 명세로 go-stablenet을 이어서 평가한다.

## 2. 표본

### 정답 원천

grpc-go에서 머지된 PR이다. 표본 규칙은 실행 전에 고정하고, 결과를 본 뒤 바꾸지 않는다.

- **기간**: 2026-01-01부터 2026-10-21까지 머지된 PR
- **의도 정답**: PR의 `Type:` 라벨을 CKS 의도 값에 대응시킨다

|라벨|의도|
|---|---|
|Type: Bug|bug_fix|
|Type: Feature, Type: API Change, Type: Behavior Change|feature_add|
|Type: Internal Cleanup|refactor|
|Type: Testing|test_add|
|Type: Security|security|
|Type: Documentation|docs_update|

- **제외 규칙**: 제외한 PR은 모두 이유와 함께 기록한다.
  - 대응하는 라벨이 없거나 둘 이상 대응하는 PR
  - 다른 PR을 옮겨 온 cherry-pick, `ci:`·의존성·릴리스 PR
  - 시험이 아닌 `.go` 파일을 바꾸지 않은 PR (단, test_add와 docs_update는 해당 파일을 정답으로 둔다)
  - 시험이 아닌 `.go` 파일을 10개 넘게 바꾼 PR. 정답이 너무 넓어 "한 번에 찾기"를 잴 수 없다
  - 생성 파일(`*.pb.go`)만 바꾼 PR
- **크기**: 남은 PR을 PR 번호순으로 정렬하고, 의도별로 고르게 최대 100건을 뽑는다. 의도 하나가 30건을 넘지 않게 한다.

### 정답 코드

변환 스크립트가 PR마다 만든다. 사람이 줄 번호를 옮겨 적지 않는다.

- **기준 커밋**: PR이 머지된 커밋의 첫 번째 부모. 색인과 정답 위치는 모두 이 커밋 기준이다.
- **정답 함수**: diff에서 기준 커밋 쪽(바뀌기 전)의 바뀐 줄을 찾는다. 그 줄을 감싸는 함수나 메서드, 타입 선언의 범위를 정답으로 삼는다. 범위는 기준 커밋의 원본 파일을 Go 표준 파서(`go/ast`)로 읽어 정한다. 평가 대상인 CKG 그래프에서 가져오지 않는다. 정답이 측정 대상에 기대면 안 되기 때문이다.
- **새로 추가된 파일과 함수**: 기준 커밋에는 없으므로 찾을 수 없다. 개수만 따로 세고 hit 지표에서는 뺀다.
- **시험 파일과 생성 파일**: 따로 표시하고 기본 지표에서는 뺀다.
- **고정**: 각 정답 범위에는 선언 줄을 앵커로 붙인다. `cks eval --verify-anchors`가 실행 전에 범위가 어긋나지 않았는지 확인한다.

### 질문

PR 제목과 설명을 바탕으로 개발자가 묻는 말투의 질문을 하나 쓴다. 질문은 AI가 쓰고, 표본 확인 때 사람이 본다.

- 정답 함수·메서드·타입 이름, 그 리시버 타입 이름, 바뀐 파일의 이름은 넣지 않는다. 패키지 경로의 낱말(예: xDS, transport)은 개발자가 영역을 가리킬 때 실제로 쓰는 말이라 허용하되, 질문마다 쓴 낱말을 기록한다.
- 변환 스크립트가 질문에 위 이름이 들어갔는지 자동으로 검사하고, 걸리면 그 질문을 다시 쓴다.
- 증상, 동작, 요구 사항으로 묻는다. 예: "연결이 끊겼다가 다시 붙을 때 예전 설정이 잠깐 쓰이는 문제를 고치고 싶어"
- 언어: 한국어로 쓴다(사용자 결정). 코드와 PR은 영어이므로, 한국어 질문에서 영어 코드를 찾는 능력도 함께 재게 된다. 질문 안의 영어 낱말도 누설 검사 대상이다.

## 3. 색인

PR마다 기준 커밋으로 DB를 만들면 정확하지만 시간이 많이 든다. 그래서 스냅샷 몇 개를 공유한다.

- 기준 커밋을 시간순으로 묶어 스냅샷 커밋 5개 안팎을 정한다. 스냅샷은 묶음의 가장 이른 기준 커밋보다 앞서야 한다.
- 어떤 PR을 스냅샷에 붙이려면, 그 PR의 정답 범위 내용이 스냅샷과 기준 커밋에서 바이트 단위로 같아야 한다. 다르면 그 PR의 기준 커밋으로 따로 색인한다.
- 이렇게 하면 수정된 뒤의 코드가 색인에 섞이지 않는다.
- 색인은 `cks setup`으로 만든다. 임베딩은 로컬 Ollama `bge-m3`를 쓴다. 유료 모델은 쓰지 않는다.

## 4. 실행과 비교 대상

- **CKS**: `cks eval --record-responses`로 시나리오를 실제 MCP 경로(`context.get_for_task`)로 돌린다. 평가 대상은 이 결과다.
- **비교 대상**: 같은 질문과 같은 색인을 각 엔진의 검색 명령에 직접 넣는다. CKS 설정에는 단계를 끄는 스위치가 없고, `cks eval matrix`는 온톨로지와 knowledge 조합만 바꾸므로 쓰지 않는다.

|비교 대상|명령|
|---|---|
|벡터만|`ckv query --json -k 10`|
|벡터와 BM25 재정렬|`ckv query --json -k 10 --bm25-rerank`|
|그래프 낱말 검색|`ckg query`|
|grep|질문에서 뽑은 낱말로 `rg`를 돌려 많이 맞은 파일 순으로 순위를 매김|
- 모든 실행에서 오류, 시간 초과, 정답 없음도 분모에 남긴다.

## 5. 지표

|기준|지표|계산|
|---|---|---|
|1번 의도|의도 정확도|응답 묶음의 `intent`가 정답 의도와 같은 비율. unknown은 틀린 것으로 센다. 의도별 혼동표를 함께 낸다|
|2번 찾기|hit@1, hit@3|정답 함수와 겹치는 인용이 1위, 3위 안에 있는 PR의 비율|
|2번 찾기|MRR|첫 정답 인용 순위의 역수 평균|
|2번 관련 코드|관련 회수율|PR이 바꾼 정답 함수 가운데 응답에 들어온 비율|
|압축|토큰|응답 전체 토큰 수, 첫 정답까지의 토큰 수|

정답 겹침은 `cks eval`의 기존 겹침 판정(같은 파일에서 줄 범위가 겹침)을 쓴다.

## 6. 만들거나 고칠 것

1. **`cks eval`에 기대 의도 필드를 더한다.** 지금 시나리오의 `intent`는 도구에 그대로 넘어가 분류기를 건너뛴다. 그래서 의도 파악을 잴 수 없다. 도구에 넘기지 않는 `expected_intent`를 더하고, 보고서에 분류된 의도와 일치 여부, hit@1, hit@3을 넣는다.
2. **PR 변환 스크립트를 만든다.** PR 목록 수집, 제외 규칙 적용, 기준 커밋 계산, diff를 함수 범위로 바꾸기, 앵커 붙이기, 스냅샷 배정, 질문 누설 검사를 한다. 질문 문장 자체는 쓰지 않는다. 변조 시험을 함께 만든다.
3. **비교 대상 실행 스크립트를 만든다.** 위 네 명령의 결과를 같은 정답 판정과 지표로 채점한다.
4. 결과는 새 패킷으로 봉인한다. 시나리오, 원응답, 지표, 제외 목록, 표본 확인 기록을 담는다.

## 7. 사람이 확인할 것

- 이 명세 (owner-acceptor)
- 정답 표본: 무작위 10건의 정답 함수가 PR 의도와 맞는지
- 질문 표본: 무작위 10건이 정답을 흘리지 않는지, 개발자가 실제로 물을 만한 말투인지

확인 결과는 사용자 메시지 그대로 기록한다. AI가 대신 확인하지 않는다.

## 8. 한계

- PR은 의도와 상관없는 부수 변경을 담을 수 있다. 정답 표본 확인으로 줄이지만 없앨 수는 없다.
- 질문을 AI가 쓰므로 말투가 실제 개발자와 다를 수 있다.
- 새로 추가된 코드는 "어디에 넣을지"를 묻는 질문이라 이 평가로는 잴 수 없다.
- 스냅샷 공유로 색인 시간을 줄이지만, 스냅샷에 붙지 못한 PR이 많으면 색인 시간이 늘어난다. 벡터 임베딩 시간은 아직 재지 않았다.
- 결과는 grpc-go 한 프로젝트의 수치다. "어떤 프로젝트든"은 go-stablenet 결과까지 보고 판단한다.
