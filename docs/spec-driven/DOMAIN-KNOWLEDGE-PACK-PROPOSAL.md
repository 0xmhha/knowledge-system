# D5 제안: 산업·조직 도메인 팩과 구현 결정의 이유

상태: **설계 제안, 사용자 결정 전** (2026-09-30). D1에서 승인된 20개는 CKS가 소스·청크·심볼·명세·근거·검증을 다루는 **공통 메타모델**이다. 블록체인·의료·제조 등 산업 지식과 한 조직의 업무 정책을 20개 안에 고정하지 않는다. 이 제안이 승인되기 전에는 현행 CLI가 아래 팩 구문을 읽는다고 주장하지 않는다.

## 문제 정의

코드는 의사결정의 산출물이다. AST는 현재 구현의 구조와 호출·데이터 흐름을 보여 주지만, 특정 규칙을 택한 이유, 거절한 대안, 현재 유효한 정책, 정책을 승인한 주체를 일반적으로 증명하지 못한다. 테스트는 관찰된 동작을 확인할 수 있지만 업무상 *왜* 그것이 옳은지는 원천 정책/결정 기록이 필요하다. 따라서 “코드에서 추출한 사실”과 “사람·문서가 제공한 의도”를 다른 원천/상태로 보관하고, 둘의 연결을 별도로 검토한다. 소스만으로 설명할 수 없는 이유는 `unknown`으로 반환한다.

## 권고 계층

| 계층 | 소유 내용 | 예 | 변경 주체 |
|---|---|---|---|
| 공통 20개 | 프로젝트·스냅샷·코드·검색·근거·스펙·검증의 공통 좌표 | `code-symbol`, `requirement`, `evidence-span` | CKS 제품/스키마 |
| 공통 결정 지식 팩 | 도메인과 무관한 의사결정의 이유·대안·가정·제약·예외 | `design-decision`, `rationale`, `assumption`, `alternative`, `constraint` | CKS 기본 팩, 사용자 확장 가능 |
| 산업/기술 팩 | 산업의 개념·행위·관계·불변식의 재사용 초안 | 블록체인/EVM의 `contract`, `transaction`, `transfer`, `authorization` | 팩 유지관리자/전문가 |
| 조직·프로젝트 오버레이 | 실제 제품 정책·용어·예외·ADR·버전별 범위와 근거 | 특정 프로젝트의 전송 한도·승인 절차 | 프로젝트 소유자/도메인 전문가 |
| 원천 인스턴스 | 위 타입으로 분류된 실제 파일·요구·결정·심볼·테스트와 검토된 관계 | 정책 BR-17 → 결정 ADR-04 → `Transfer` → 테스트 | 검토 워크플로 |

블록체인 팩도 단일 “정답 산업 모델”로 취급하지 않는다. 체인·VM·프로토콜·제품 유형에 따라 의미가 달라지므로 `industry.blockchain`의 광범위한 어휘와 `platform.evm` 같은 하위 팩을 분리한다. 재사용 팩은 질문과 제약의 **초안**을 제공하고, 무엇이 그 프로젝트에서 실제 정책인지는 사용자가 근거를 넣어 승인한다.

## 사용자가 채우는 영역

설치형 CKS는 예를 들어 다음과 같은 프로젝트 소유 파일을 읽도록 확장한다. 이는 **제안 경로/구문**이며 현행 `ExtractOntology`의 입력 형식이 아니다.

```text
.cks/knowledge/manifest.yaml          # 사용할 팩과 버전/다이제스트, 프로젝트 범위
.cks/knowledge/domain/*.yaml           # 프로젝트 업무 객체·행위·관계·불변식
.cks/knowledge/policies/*.yaml         # 정책의 원문, 소유자, 유효 범위/기간, 예외
.cks/knowledge/decisions/*.md          # ADR: 문제, 선택, 이유, 대안, 근거, 변경 이력
.cks/knowledge/questions/*.yaml        # 답해야 할 업무 질문·수용 기준
```

온보딩에서는 “핵심 업무 객체/행위는 무엇인가?”, “어떤 정책이 동작을 제한하는가?”, “그 규칙의 승인 근거는 어디에 있는가?”, “대안과 예외는 무엇인가?”, “어떤 코드·테스트가 이를 구현/검증하는가?”를 작은 양식으로 받는다. 기존 ADR, 제품 명세, 정책 문서, 사고 후 분석, 이슈·PR 설명은 후보 원천으로 수집할 수 있지만, LLM 추출 결과는 `proposed`이며 담당자가 원문을 보고 승인해야 한다. 사람이 내용을 작성하지 않았거나 기록이 없는 부분은 빈칸과 `unknown`으로 남긴다.

## 팩 계약 초안

팩에는 `pack_id`, `schema_version`, 의미 버전, 소유자, 의존 팩/버전, 적용 범위(프로젝트·서브시스템·체인 등), 원천 다이제스트, 개념과 용어, 관계의 주체/객체 타입·방향·카디널리티, 제약, 능력 질문을 둔다. 내부 ID는 팩별 로컬 ID를 허용하되 조인 키는 `(pack_id, concept_id)`로 만든다. 기존 20개 ID는 `core` 팩에 매핑해 이전 경로를 유지한다. 하위 팩의 덮어쓰기는 묵시적으로 허용하지 않는다. `extends`/`maps_to` 같은 명시적 매핑과 스키마 검증을 거치고, 서로 다른 뜻의 같은 단어는 여러 후보로 남긴다.

각 **실제 정책/결정/관계 인스턴스**에는 원천 파일·줄/문서 ID·해시, 작성/승인 주체, 상태(`proposed|verified|rejected|stale`), 적용 범위, 유효 버전/기간, 대체/폐기 관계를 둔다. 충돌하는 정책의 우선순위는 산업 팩이 임의로 정하지 않는다. 프로젝트 소유자가 명시적 우선순위·예외·적용 시점을 승인하거나 CKS는 `conflict`로 기권한다. 팩 자체도 데이터셋 빌드 입력에 넣어 팩/정책 버전이 바뀌면 새 `dataset_id`를 만든다. 인용 권한은 원천 파일의 접근 정책을 따라야 한다.

데이터 구조는 현행 CKS 의미 투영/CKG/CKV 위에서 구현할 수 있다. RDF/OWL 전체를 필수로 도입할 필요는 없다. 관계 타입·필수 속성·카디널리티 검증은 [W3C SHACL의 데이터 그래프/형상 그래프 구분](https://www.w3.org/TR/shacl/)을 참고할 수 있고, 생성물·활동·책임 주체와 변경 계보는 [W3C PROV-O](https://www.w3.org/TR/prov-o/)에 대응시켜 내보낼 수 있다. 이는 표준과의 개념적 정렬 제안이지 현행 RDF/SHACL 구현 주장이나 그 표준에 대한 준수 선언이 아니다.

## “왜 이 코드인가?” 경로

예를 들어 사용자가 제공한 프로젝트 정책 `BR-17`이 “한도를 넘는 전송은 별도 승인을 요구한다”라고 정하고, `ADR-04`가 승인 검사를 서비스 경계에 두기로 결정했다고 하자. CKS가 검토된 관계를 아래처럼 연결한다.

```text
정책 BR-17 --CONSTRAINS--> 전송 행위
결정 ADR-04 --DECIDED_BECAUSE--> BR-17
결정 ADR-04 --REJECTED_ALTERNATIVE--> 다른 검사 위치
요구 R-12 --DERIVED_FROM--> BR-17
요구 R-12 --IMPLEMENTED_BY--> CKG 심볼 TransferService.checkApproval
수용 기준 AC-12 --CHECKED_BY--> CKG 테스트 TestApprovalLimit
테스트 실행 --OBSERVED--> 결과 스냅샷
```

이 경로는 **사용자가 제공하고 검토한 정책·결정·명세가 있을 때** 설명을 만든다. 코드 조건문이나 테스트 이름에서 `BR-17`의 이유를 역으로 만들어내지 않는다. 각 화살표는 타입·방향·양쪽 원천·현재 스냅샷·검토자를 요구한다. 기존 20개의 `criterion-decision`은 수용 판정 사건이고, 제안한 `design-decision`은 선택과 이유의 기록이므로 의미가 다르다. 기존 `policy`는 CKS 색인/접근 정책이므로 업무 정책은 프로젝트 도메인 팩의 별도 타입으로 다룬다.

## LLM 코딩 경로와 안전한 사용

1. 작업 요청에서 프로젝트/서브시스템과 관련 팩을 고정하고 원문 CKV/CKG 검색을 수행한다.
2. 검색된 코드의 CKG 심볼에서 검토된 요구·정책·결정·테스트 관계를 따라가며 각 원천/버전을 재검증한다.
3. `evidence-pack`에 구현 위치, 현재 동작, **왜/어떤 제약 때문에**, 모호성·충돌·미확인 항목을 구분해 넣는다. 검색된 일반 문맥과 규범성 있는 정책을 같은 권위로 취급하지 않는다.
4. LLM은 이 근거로 변경안을 만들고, 정책 불변식과 수용 기준을 테스트한다. 패치는 `patch-attempt`에 남기고 `criterion-decision`으로 사람이 의미 충족을 판단한다.
5. 근거가 부족하거나 정책이 충돌하면 CKS는 확정 이유를 생성하지 않고 필요한 검토 질문과 출처를 반환한다. 기본 CKV+CKG 검색 후보는 보존한다.

Palantir의 공개 문서는 조직의 실제 데이터에 개념을 연결하는 객체·관계 모델과, 행위·논리·보안을 결합한 결정 모델을 설명한다. 따라서 “파트너마다 동일한 개념 목록을 쓴다”는 해석보다 **공통 구조를 갖되 실제 객체·행위·규칙을 조직별로 모델링한다**는 해석이 이 설계에 가깝다. ## D5에서 결정할 항목과 검증 오라클

| 결정 | 권고 | 반증 가능한 검사 |
|---|---|---|
| D5-01 팩 계층/범위 | 공통 20 + 공통 결정 팩 + 선택 산업/기술 팩 + 프로젝트 오버레이 | 도메인 팩 없는 저장소도 기존 CKV+CKG/CKS 경로를 그대로 사용 |
| D5-02 신원/버전 | `(pack_id, local_id)`와 명시적 의존/적용 범위; 팩 바이트를 데이터셋 입력에 포함 | 같은 코드라도 서로 다른 팩/정책이면 다른 `dataset_id`; 구 ID 읽기 보존 |
| D5-03 출처/권위 | 정책·결정·관계마다 원문/검토자/유효 범위; 충돌은 기권 | 무근거 “왜” 생성 0건, 오래된 정책의 현재 적용 0건, 충돌 진단 |
| D5-04 타입/관계 검증 | 관계 주체/객체·방향·카디널리티와 팩 충돌 검사 | 잘못된 관계, 중복 ID, 누락 의존, 팩 덮어쓰기 거부 |
| D5-05 코딩 문맥 | 원문 검색 우선, 검토된 정책/결정 경로를 제한 예산으로 첨부 | 기본 후보 보존, 출처 누락/권한 위반/예산 초과에서 명시적 폴백 |
| D5-06 파일럿 | `knowledge-system` 자체의 결정/정책 사례 + 선택형 블록체인 예시 + 비블록체인 대조 | 한 산업 개념이 무관 프로젝트에 누출되지 않음; 원천 근거 없는 관계 승격 거부 |

**설계 영향:** D1의 20개 타입 정의는 유지한다. 그러나 “어떤 산업의 프로젝트에도 설치해 도메인 정책과 구현 이유를 제공한다”는 제품 목표에는 이 D5가 빠져 있으므로, 해당 목표에 한해 상세 설계 폐쇄를 다시 점검해야 한다. 사용자가 D5 범위와 팩 계약을 결정하면 WBS A5.1/A5.2/A6/A8 및 B0의 수용 조건과 이전 경로를 먼저 갱신한 뒤 구현한다.
