# Knowledge System 요구사항·설계·WBS 재기준선 v2

작성일: 2026-09-30 · 파일럿: `knowledge-system` · 임베더: 로컬 Ollama · 대상: macOS arm64, Linux arm64/amd64

## 1. 판정과 개발 순서

기존 v0.1 요구사항(`study/docs/reviews/knowledge-system/spec-driven-requirements.md`)의 FR-01–10, INV-01–07, NFR-01–05와 S-01–09는 유지한다. 이 문서는 사용자의 새 순서에 맞춰 **완료 조건과 선행 관계를 대체**한다. v0.1 WBS는 이력 자료이며, 아래 v2가 이후 작업의 실행 기준이다. [`END-TO-END-DESIGN.md`](./END-TO-END-DESIGN.md)는 A/B/C 전 구간의 선행 설계 기준선이고 `EXECUTION.md`는 구현 증거의 원장이다.

1. **A: 모델 독립 리팩토링·개발.** A/B/C 전 구간의 상세 설계는 구현 전에 `END-TO-END-DESIGN.md`에서 먼저 고정한다. 결정적 mock 임베더, 가짜 Ollama HTTP 서버, 고정 Git 픽스처와 실제 CKV/CKG/CKS 실행으로 구조·정확성·안전성·호환성·설치 경로를 검증한다. 실모델 품질 수치 없이 이 단계를 완료할 수 있다.
2. **B: 실모델 평가.** 지정된 로컬 Ollama 모델과 승인된 질문 정답을 한 코퍼스/하드웨어에서 고정한다. CKV, CKG, CKS 및 온톨로지 ablation의 품질·지연·비용을 측정한다.
3. **C: 평가 결과 기반 재리팩토링.** B에서 관측된 실패/회귀를 스펙·테스트에 먼저 반영하고 병목/정확성 패치를 한다. 동일 조건 재평가 후 기본 활성화와 출시를 결정한다.

**게이트 분리:** A의 구조 게이트가 통과해도 `natural_language_quality=unmeasured`, `ontology_runtime=disabled`, `release=preview`다. B/C의 품질 게이트는 건너뛰거나 성공으로 표기하지 않는다. 사용자에게 실모델 평가를 미루겠다는 요청은 A의 구현을 허가하지만 B의 합격을 뜻하지 않는다. 패키지 자체의 대상 OS/CPU 실행 검증은 A에서 수행한다. 실모델이 필요한 설치 시나리오는 B로 둔다.

## 3. A 단계의 상세 설계 결정

### 3.1 ID와 불변 데이터셋

`project_id`는 소스 경로나 Git remote에서 매번 유도하지 않는다. `cks init --project-id`로 사람이 지정한 고유 문자열을 저장하거나 없으면 안전한 난수 ID를 한 번 생성한다. 설정을 다시 로드해도 같아야 하며 다른 프로젝트의 같은 ID가 한 데이터셋 루트에 들어오면 거부한다. `snapshot_id`는 `committed`에서 Git SHA와 파일/정책 다이제스트, `working-tree`에서 Git SHA·수정/신규 파일·정책 다이제스트, 비Git `snapshot-only`에서 파일/정책 다이제스트를 포함한다. `dataset_id`는 빌드 전 알 수 있는 프로젝트·스냅샷·그래프/벡터/의미 **원본 입력·정책의 다이제스트**·임베딩 정체성·스키마/빌드 플랫폼으로 계산한다. 생성 텍스트와 출력 그래프/벡터/의미 다이제스트는 순환 신원을 피하기 위해 `dataset_id` 계산에 넣지 않고 완료 매니페스트에서 별도로 검증한다. 사람이 주는 `--version` 이름은 별칭일 뿐 ID가 아니다. 정렬 검사는 이 필드가 비어 있는 구버전을 `legacy_unpinned`으로 분류하고 새 의미 승격/작업 트리 인용에서는 거부한다.

`SOURCE-SNAPSHOT-ADR.md`는 원문 보관, Git 이력, 빌드 중 변경, 인용 및 마이그레이션의 세부 계약이다. 구현 전 기술 검증 항목을 ADR에서 명시한다. 이 항목이 통과하지 않으면 `working-tree`/`snapshot-only`를 노출하지 않고 기존 `committed` 모드를 유지한다.

### 3.2 Ollama 정체성과 실패 정책

색인/질의 임베더는 `provider/model/model_digest/dim/target_dim/pooling/normalization/query_prefix_policy/identity_version`을 함께 비교한다. 정확한 모델명 선택·다이제스트 조회는 Ollama [모델 목록 API](https://docs.ollama.com/api/tags), 차원 확인은 [임베딩 API](https://docs.ollama.com/api/embed)를 사용한다. 조회 실패나 같은 이름의 모호한 응답은 실패다. 색인 시작·종료와 각 배치 전후, 질의 열기에서 다이제스트를 비교한다. 빌드 중 변경은 후보 실패, 질의 시 변경은 `reindex_required` 오류다. 기존 Ollama 색인에 다이제스트가 없으면 실모델 질의를 조용히 열지 않고 재색인을 안내한다. mock/기타 제공자는 동일 스키마를 쓰되 검증 불가능한 다이제스트를 Ollama 다이제스트로 위장하지 않는다. 모든 HTTP 테스트는 로컬 가짜 서버와 고정 응답으로 실행한다. 태그의 동시 악의적 ABA 변경은 신뢰된 로컬 데몬이라는 운영 경계 밖이다.

### 3.3 검토된 온톨로지의 런타임 경계

CKS가 원문 질의를 먼저 CKV/BM25/정확 심볼 검색에 보낸다. 개념 후보는 복수로 유지하고 `verified` 관계만 이미 선택된 인용의 소프트 점수에 영향을 준다. 추적과 문맥 주석은 보관된 원문·스냅샷·줄을 재검증한다. 질의 시간·후보·확장 홉·토큰 상한에 걸리거나 의미 저장소가 없으면 기본 경로로 돌아가며 명시적 상태를 남긴다. 제안/미검토 개념은 검토 UI에서만 사용한다. 런타임 플래그는 B의 ablation 결과 전까지 기본 꺼짐이다.

### 3.4 개발·설치 계약

스펙 `verified`는 내용 승인, 추적 `linked`는 관계 존재, 테스트 `pass`는 특정 실행 성공, 요구사항 `accepted`는 별도 사람 판정이다. 이 네 상태를 합치지 않는다. 외부 패치는 `patch_id`, 기준 스냅샷, 결과 스냅샷, Git 입력일 때의 기준·결과 커밋, 수정 파일 다이제스트, 실행 명령·환경, 기준별 판정, 재색인 데이터셋 ID를 연결한다. 실패 패치는 승격되지 않는다.

지원 대상은 macOS arm64와 Linux arm64/amd64로 설계한다. 대상별 네이티브 빌드·압축 해제·의존성·체크섬·라이선스 확인 및 세 독립 프로젝트 스모크를 통과해야 그 대상을 `supported`로 표기한다. 빌드 이미지에서만 실행한 결과는 `preview`다. `doctor`는 로컬 Ollama가 없으면 구조/텍스트 기능과 실제 의미 검색 불가를 구분한다. `cks index/status/serve/rollback`은 기존 `setup/mcp`의 얇은 호환 명령으로 구현하며 상태 JSON에는 지원 능력과 결손 이유를 넣는다.

### 3.5 매니페스트/CLI 이전 순서

새 데이터셋 매니페스트는 스키마 v2로 `project_id`, `snapshot_id`, `dataset_id`, `source_mode`, `source_commit`, `file_manifest_digest`, `embedding_identity_version`을 필수로 쓴다. 한 빌드의 CKG/CKV/CKS가 같은 좌표를 내놓지 못하면 후보를 폐기하지 말고 실패 상태로 남기며 활성 포인터를 건드리지 않는다. v1은 현재 커밋형 조회만 허용하는 `legacy_unpinned` 읽기 경로로 유지한다. v1 파일을 제자리 덮어쓰거나 빠진 ID를 경로에서 추측하지 않는다. `cks status`에는 `reindex_required`와 이유를 표시한다. `cks setup`과 기존 MCP 입력은 유지하고 새 `index/serve/rollback` 명령은 같은 내부 작업을 호출한다. 공개 JSON의 기존 필드는 제거하지 않고, 새 필드는 소비자가 모를 때 무시 가능한 범위에서만 추가한다. 작업 트리 인용은 `SOURCE-SNAPSHOT-ADR.md`의 버전 협상 전에는 구 소비자에게 내보내지 않는다.

### 3.6 외부 패치와 수용 판정 상태 기계

`PatchAttempt`는 `patch_id`(호출자가 발급한 유일 ID), `project_id`, `base_snapshot_id`, 변경 파일 목록/다이제스트, `result_commit` 또는 작업 트리 스냅샷, 실행된 검사 보고서 ID, 후보 `dataset_id`, 생성 시각을 가진 불변 기록이다. 같은 `patch_id`에 다른 바이트를 다시 쓰면 거부한다. 수용 기준별 `CriterionDecision`은 `criterion_id`, 명세 버전, 근거 인용, 테스트 보고서 ID, 검토자, `approved|rejected|needs_review`와 이유를 별도로 기록한다. 모델이 만든 계획·테스트 통과만으로 `approved`를 쓰지 않는다.

상태는 `proposed → built → tests_passed|tests_failed → reviewed → promoted|rejected`다. 테스트 실패/소스 변경/기준 충돌에서는 `current`를 유지하고 보고서만 보존한다. `reviewed`에 도달하려면 새 커밋의 CKV/CKG/CKS 정렬과 모든 필수 기준의 사람 판정이 있어야 한다. 기존 `cks semantic test`와 `setup --gate-test-*`는 검사 보고서를 제공하지만, 새 패치 기록으로 자동 승격하지 않는다. 이 절차는 코드 작성 에이전트에 의존하지 않으며 외부 도구가 생성한 패치를 받는 읽기/검증 경계다.

## 5. 기능별 검증과 완료 정의

모든 A 작업은 정상·실패·구버전·두 프로젝트·두 스냅샷 중 해당되는 조합을 명시한다. 직접 단위 시험, 실제 CKV/CKG/CKS 통합 시험, 공개 CLI/MCP 호환 시험을 구분한다. 위험 경로에는 실패 주입을 먼저 추가한다. 승인되지 않은 요구사항/온톨로지는 fixture 안에서만 `verified`가 될 수 있고 생산 파일은 계속 `proposed`다.

**A 완료:** A0–A8 증거 전부, 대상별 구조 설치 스모크, 새 매니페스트 계약, 작업 트리 원문 보관과 과거 인용 재현, known limits 및 마이그레이션 문서. 품질 상태는 `unmeasured`로 남긴다. **B 완료:** 승인된 실모델 질문셋과 임계치에 대한 원자료/재현 보고서. **C 완료:** B에서 확인한 회귀를 수정하고 같은 조건으로 재검증, 기본 기능/릴리스 결정. WBS 전체 완료는 A+B+C가 모두 통과한 뒤에만 표시한다.

**판정:** 이 v2는 구현 순서, 요구사항 추적, 실패 판정과 검증 산출물을 정리한 WBS 기준선이다. 사용자가 D1–D4 **설계 결정**을 승인했다. D1-02의 `CHECKED_BY`는 승인된 D3 계약의 개정으로 기록했다. 20개 타입의 정의와 데이터 흐름은 [`ONTOLOGY-20-USAGE.md`](./ONTOLOGY-20-USAGE.md)에 있다. 실제 v2 기능 검증은 A의 수용 시험으로 남는다. 판정 증거는 [`DESIGN-GATES-EVIDENCE.md`](./DESIGN-GATES-EVIDENCE.md)에 있다. 실모델 수치와 그 결과에 따른 기본값 결정은 사용자의 순서대로 B/C에서 수행한다. 설계 폐쇄, 구현 완료, 품질 승인을 별도로 기록한다.

**D5 확장:** 사용자는 공통 20개를 고정하고 공통 틀·조직별 모델을 분리하는 **D5-01 방향**에 동의했다. R2-09–11과 A5.4/A5.5/A6/A7.1/A8/B0/B1에 [`DOMAIN-PACK-CONTRACT-V1.md`](./DOMAIN-PACK-CONTRACT-V1.md)의 상세 계약과 검증을 반영했다. D5-02–07의 세부 설계는 검토안이며, 구현 전에 선택한 파일럿·원천 위치·검토 역할을 고정한다. D1–D4 승인과 D5 방향 동의를 산업 도메인 팩 구현 완료로 확대 해석하지 않는다.
