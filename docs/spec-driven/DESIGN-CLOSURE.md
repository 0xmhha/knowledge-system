# WBS 설계 완결성 검토 — 2026-09-30

## 결론과 확정된 범위

**이력 문서:** 이 검토 시점에 WBS v0.1의 상위 아키텍처, 기능 요구사항, 단계별 수용 기준은 작성됐지만 상세 설계는 완결되지 않았다. 이후 [`END-TO-END-DESIGN.md`](./END-TO-END-DESIGN.md)에 A/B/C 전체의 목표 계약을 작성했다. 상세 설계의 폐쇄 여부는 그 문서 11절의 D1–D4 게이트로 판정한다. 어느 문서도 구현·품질·배포 게이트 통과를 뜻하지 않는다. PDF 인용과 설계 동기는 `study/docs/reviews/knowledge-system/ckv-ckg-ontology-installation-proposal.md`에, 원 요구사항과 WBS는 같은 디렉터리의 `spec-driven-requirements.md`와 `spec-driven-wbs.md`에 있다. PDF의 설명은 도메인 근거이고 아래 인터페이스는 프로젝트 설계다.

**2026-09-30 순서 변경:** 사용자는 실모델 평가를 개발 뒤로 미루고, 그 결과로 재리팩토링하기로 했다. 이후 실행 기준은 [`DELIVERY-PLAN-V2.md`](./DELIVERY-PLAN-V2.md)다. 기존 아래 설명에서 실모델 평가가 선행 조건으로 적힌 곳은 v2의 **A(모델 독립 개발) → B(실모델 평가) → C(평가 후 재리팩토링)** 순서로 읽는다. A의 구조 게이트는 실모델 없이 통과 가능하지만 WBS 전체 완료와 자연어 품질 승인은 B/C까지 필요하다.

## 1. 로컬 Ollama와 동일 벡터 공간 계약 (INV-07, W0.1, W3.5)

Ollama의 [임베딩 API](https://docs.ollama.com/api/embed)는 `/api/embed`에서 벡터를 생성하고, [모델 목록 API](https://docs.ollama.com/api/tags)는 이름과 다이제스트를 반환한다. 설계상 질의용 임베더와 색인용 임베더는 `provider`, 모델 이름, **모델 다이제스트**, 벡터 차원, 차원 축소, 쿼리 접두사 정책을 함께 고정한다. 현재 `EmbeddingIdentity`는 provider·name·dim·pooling·normalization만 비교한다. 같은 Ollama 태그가 다른 모델 바이트를 가리키는 경우를 검출하지 못하므로 상세 구현이 남아 있다.

1. 색인 직전 Ollama 모델 목록에서 선택 모델의 정확한 다이제스트를 얻는다. 이름의 `:latest` 정규화와 중복 이름을 명시적으로 처리하며, 다이제스트가 없으면 실모델 색인을 실패시킨다.
2. 벡터 매니페스트에 `model_digest`, `query_prefix_policy`, `embedding_identity_version`을 기록한다. 임베딩 시작과 끝에서 다이제스트를 다시 읽고 달라지면 후보를 승격하지 않는다. 질의 시작 시에도 일치 여부를 확인한다. 기존 매니페스트에는 구버전 상태를 표시하고 재색인 경로를 제공한다.
3. API 연결 실패, 모델 미설치, 차원 불일치, 다른 다이제스트, 쿼리 접두사 불일치가 각각 구별되는 오류가 되도록 한다. 임베딩 모델 이름과 차원만 같은 경우를 성공으로 취급하지 않는다.

**검증:** 가짜 Ollama HTTP 서버가 같은 태그/차원에 다른 다이제스트를 반환할 때 색인 후보와 질의 열기를 거부한다. 실제 모델에서는 모델 다이제스트·차원·Ollama 버전·하드웨어를 보고서에 고정한다. 로컬 서버에서 모델 목록을 확인하기 전 특정 모델의 실측 품질을 주장하지 않는다.

## 2. 실모델 평가 설계 (W0.1, W1.3/1.6/1.7, W3.5)

`knowledge-system`의 한 **고정 Git 커밋**에서 코퍼스를 빌드한다. 기준선과 변경 후보는 같은 Ollama 모델 다이제스트, 차원, 쿼리 접두사, 코퍼스, 질문, top-K, 필터, 하드웨어를 사용한다. 커밋이 달라지면 서로 다른 실험으로 취급한다.

평가셋은 코드 심볼, 긴 Markdown의 끝 단락, 한국어·영어 용어, 다의어, 답이 없는 API, 문서/코드 충돌, 오래된 인용, 복수 프로젝트 격리를 분리한다. 각 질문에 정답 파일·줄/필요한 지식 범위·기권 여부·기대 커밋을 리뷰어가 기록한다. `cks eval`의 `retrieval_state`, `evidence_state`, `abstention_state`, `snapshot_state`를 별도로 집계한다. 생성 답변의 근거 적합도는 이 도구가 측정하지 않으므로 별도 판정으로 둔다.

각 실험은 최소한 Recall@K, MRR, 무관 인용률, 기권 적합도, 인용 커밋 충돌, warm p50/p95, cold 시작 지연, 색인 시간·크기를 기록한다. 모델 호출 지연과 CKS 합성 지연을 분리한다. 온톨로지는 기본 CKV+CKG, 개념 텍스트만, 그래프 관계만, 둘을 함께 사용한 경로를 동일 질문군에서 비교한다. 오개념 확정률과 기존 후보 손실을 확인하기 전 런타임 재순위는 기본값으로 켜지 않는다.

수치 임계치는 실모델 기준선과 질문 정답을 확정한 뒤 정한다. 현재 임의의 Recall·p95 합격 숫자를 쓰지 않는다. 측정 불능은 `pending`이며 `pass`가 아니다.

## 3. 파일럿 온톨로지 승인 계약 (W2.3, W3.1–W3.5, W4)

`docs/spec-driven/ontology-pilot.yaml`의 20개 개념과 여섯 능력 질문, `spec-pilot.yaml`의 세 요구사항은 **D1 설계 승인·개별 원천 검토 대기** 상태다. 타입 정의의 승인과 실제 투영 항목의 `verified` 승격은 별개다. 20개 타입의 사용 경로는 [`ONTOLOGY-20-USAGE.md`](./ONTOLOGY-20-USAGE.md)에 있다.

검토자는 질문별 정답과 허용되지 않는 해석, 한영 별칭의 다의어, 누락 개념, `IMPLEMENTED_BY`와 `TESTED_BY` 근거를 같은 커밋에서 확인한다. 검토 결과에는 원천 줄, 승인자, 검토 날짜, 보류/반려 이유를 남긴다. 무근거 자동 추출 주장은 `proposed`를 유지한다. `verified`는 근거·타입·검토자·현재 스냅샷 검증이 모두 있어야 한다. 검토 비용은 표본당 시간과 수정/반려 건수로 계측한다.

검토가 끝나기 전에는 대규모 용어 색인이나 mock 검색 성공을 실제 도메인 품질로 해석하지 않는다.

## 4. 당시 남아 있던 스냅샷과 프로젝트 신원 설계 (W2.4, W5.3)

현행 `cks setup`은 안전한 `committed` 모드만 제공한다. 깨끗하지 않은 작업 트리를 거부하는 동작은 유지한다. `working-tree`는 단순히 더티 검사를 끄는 옵션으로 구현하지 않는다. 후보가 읽는 파일이 빌드 중 바뀌면 CKG와 CKV가 서로 다른 내용을 색인할 수 있기 때문이다.

제안된 완료 계약은 다음과 같다.

1. `cks init`이 사용자가 지정한 안정 `project_id`를 설정에 보존한다. 한 프로젝트의 각 후보에는 불변 `dataset_id`가 있다. 과거 인덱스의 빈 ID는 구버전으로 구별한다.
2. `working-tree` 요청은 엔진 두 개가 실제로 읽을 수 있는 파일 집합을 먼저 계산한다. 정규화한 저장소 상대 경로, 콘텐츠 SHA-256, 파일 종류, 제외 정책 버전을 정렬해 파일 매니페스트 다이제스트를 만든다. 비밀 경로·심볼릭 링크 탈출은 후보 생성에서 막는다. 수정·신규 파일을 모두 포함하고 HEAD만으로 신원을 만들지 않는다.
3. 빌드가 **불변으로 보관되는 소스 사본**을 읽도록 한다. CKG의 Git 이력과 원문 검증이 이 사본에서 어떻게 동작하는지 먼저 검증해야 한다. 그래프·벡터·의미 투영은 `project_id`, `dataset_id`, 기준 Git 커밋, 파일 매니페스트 다이제스트를 모두 기록한다. 기존 인용 계약에 작업 트리 스냅샷 ID를 안전하게 전달할 공개 필드·마이그레이션 설계도 필요하다.
4. 승격 직전 파일 매니페스트와 각 엔진의 실제 입력 목록을 대조한다. 누락, 빌드 중 변경, 서로 다른 다이제스트, 모델 신원 변경은 후보를 실패시키고 `current`를 보존한다. 런타임도 세 계층의 좌표를 재검증한다.

**S-08 오라클:** 같은 HEAD에서 한 추적 파일 수정, 한 새 파일 추가, 같은 파일을 다시 수정한 세 경우가 서로 다른 스냅샷 ID를 가진다. 옛 스냅샷의 인용은 보존되고 새 버전으로 조용히 재해석되지 않는다. 청결한 HEAD 입력은 기존 committed 경로와 동일해야 한다. 이 계약의 구체적인 사본 저장 방식과 공개 인용 마이그레이션은 구현 전 별도 ADR·실패 주입 테스트가 필요하다.

## 5. macOS arm64·Linux 배포 설계 (W5.1/5.4/5.5)

첫 지원 매트릭스는 macOS arm64와 Linux arm64·amd64 후보로 둔다. Linux CPU 아키텍처가 아직 사용자에게 확정되지 않았으므로 둘 다 검증하고 지원 여부를 결정한다. 각 대상에서 CGO·SQLite 확장과 세 바이너리를 **대상 OS/CPU에서 빌드**하며, 압축 해제한 산출물의 네이티브 의존성·체크섬·모듈 목록·라이선스를 기록한다. macOS에서 만든 바이너리를 Linux에서 실행 가능하다고 표기하지 않는다.

Linux의 깨끗한 컨테이너/호스트에서 `doctor → init → setup → CKV 질의 → CKS MCP 질의 → 실패 후보 미승격 → 롤백`을 실행한다. Go/TypeScript/미지원 코드+Markdown 프로젝트를 서로 다른 데이터셋에 설치하고 인용의 프로젝트·커밋을 확인한다. Ollama는 외부 로컬 서비스로 주입하고, 모델 미설치·서비스 중단 시 기능이 낮아진 상태를 정확히 보고한다. Docker의 Linux arm64 빌드 이미지에 SQLite 개발 헤더를 추가한 뒤 세 바이너리의 빌드·기동과 세 프로젝트의 설치·MCP 질의가 통과했다. 이는 빌드 이미지 안의 구조 검증이다. 압축 패키지의 깨끗한 런타임 이미지, Linux amd64, 실제 Ollama 품질은 별도 게이트다.
