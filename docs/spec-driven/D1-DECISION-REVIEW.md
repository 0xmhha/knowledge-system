# D1 파일럿 도메인 모델: 사용자 결정안

상태: **사용자 결정 대기** · 기준: `ontology-pilot.yaml` 18개 제안 개념, `spec-pilot.yaml` 3개 제안 요구사항/4개 수용 기준, [`DESIGN-GATES-EVIDENCE.md`](./DESIGN-GATES-EVIDENCE.md)의 코드·원천 줄 매핑. 이 문서는 판단 자료이며 개념이나 관계를 `verified`로 승격하지 않는다.

## 결정을 구분하는 원칙

D1에서는 **개념 모델의 뜻과 경계**를 결정한다. 이후 실제 소스의 개별 주장, `IMPLEMENTED_BY` 관계, 테스트 실행, 사람의 수용 판정은 각각 해당 스냅샷의 원문과 검토 기록으로 검증한다. D1 승인만으로 현재 코드가 요구사항을 충족했다고 주장하지 않는다. 실모델 검색 품질은 B/C에서 평가한다.

| ID | 사용자 결정 | 권고 | 선택에 따른 영향 |
|---|---|---|---|
| D1-01 | 파일럿 개념 범위 | 현재 18개를 기본 어휘로 유지하고 `patch-attempt`와 `criterion-decision` 두 사건 개념을 추가한다. `source-origin`은 인용 좌표/출처 데이터로 둔다. | 두 사건은 “어떤 변경을 어떤 근거로 승인했는가”를 질의할 때 필요하다. 추가 시 YAML 추출·검토 fixture 수와 관련 문서의 개념 수를 갱신한다. 단순 경로/원천은 온톨로지 개념 확장보다 provenance 필드가 정확하다. |
| D1-02 | `AcceptanceCriterion ACCEPTED_BY TestCase` 명칭 | v2의 정식 관계를 `CHECKED_BY`로 바꾸고 v1 `ACCEPTED_BY`는 읽기 호환 별칭으로만 둔다. 사람의 `accepted`는 `CriterionDecision.approved`에서만 생성한다. | 현 이름은 테스트 연결을 실제 수용으로 오해하기 쉽다. 이 권고를 채택하면 이미 승인된 D3의 공개 관계명·마이그레이션 절을 한 번 개정하고 기존 투영/소비자 골든을 보존해야 한다. 현 이름을 유지하려면 UI/API에 `link_only`를 필수 표시한다. |
| D1-03 | 자연어 용어 처리 | 일반어(`project`, `claim`, `term`, `test`)는 맥락 없이 자동 질의 확장하지 않는다. 검토된 개념의 복수 후보를 보여 주고 CKV+CKG 기본 후보 집합을 보존한다. | 한국어·영어 다의어가 한 개념으로 잘못 고정되는 위험을 줄인다. 개념 텍스트/관계의 가중치는 B 평가 전 기본 꺼짐이다. |
| D1-04 | 여섯 능력 질문의 합격 의미 | D1에서는 `DESIGN-GATES-EVIDENCE.md`의 구조 답·금지 해석을 승인한다. 실제 질문 문구의 회수율·정답 파일/줄은 B0에서 고정한다. | 실모델 평가를 뒤로 미룬 사용자 순서와 맞고, 구조 설계가 모델 점수에 묶이지 않는다. |
| D1-05 | 세 파일럿 요구사항과 네 수용 기준의 지위 | 도메인 모델의 대표 사례로 승인하되 전체 제품 명세는 FR-01–10, INV-01–07, NFR-01–05와 R2-01–08을 기준으로 유지한다. | 소규모 파일럿을 제품 전체 완료 판정으로 오해하지 않는다. 기준의 Given/When/Then 의미는 사용자가 검토하고 실제 실행·의미 판정은 별도다. |

D1-01의 추가 개념 제안은 다음처럼 한정한다.

| 개념 | 종류와 정의 초안 | 포함 / 제외 |
|---|---|---|
| `patch-attempt` | `process`: 한 기준 스냅샷에서 변경을 적용해 결과 스냅샷과 검사 증거를 만든 불변 시도 | 변경 파일 다이제스트·전후 스냅샷·검사 기록 / 코드 변경 계획만 있는 상태, 활성 승격 자체 |
| `criterion-decision` | `process`: 특정 명세 버전과 결과 스냅샷의 수용 기준을 사람이 근거와 함께 판정한 사건 | 승인·반려·재검토, 판정자·이유·근거 / 단순 테스트 성공, 연결 관계의 존재 |

두 개념은 **질의 가능한 사건 타입**으로 정의하되, 자연어 자동 확장의 기본 어휘로 넣지 않는다. 출처 `source-origin`은 `EvidenceSpan.origin_id` 및 파일 매니페스트의 좌표로 유지한다. 이것이 권고이며, 사용자가 범위를 확정하기 전 YAML에 추가하지 않는다.

## 먼저 확인할 의미 충돌

1. **프로젝트·스냅샷·데이터셋:** 같은 Git HEAD라도 작업 트리 바이트가 다르면 다른 소스 스냅샷이다. 같은 소스라도 임베딩 모델/빌드 정책이 다르면 다른 데이터셋이다. 이 세 개념을 합치면 과거 인용과 검색 결과를 잘못 조인한다.
2. **검색 청크·근거:** `VectorChunk`는 검색 단위이고 `EvidenceSpan`은 캡처된 원문 줄의 검증 단위다. 청크의 유사도 또는 CKV의 기존 `content_sha256`만으로 사실 검증을 완료하지 않는다.
3. **요구·테스트·승인:** 검토된 관계는 연결 존재, `TestExecution.pass`는 특정 실행 성공, `CriterionDecision.approved`는 사용자가 기준의 의미 충족을 승인한 사건이다. 세 상태가 모두 필요하다.
4. **모호한 용어:** 한영 별칭은 표면 표현이고 `Concept` 정의가 의미를 결정한다. 한 용어가 여러 개념에 걸리면 모두 후보로 유지한다. 제안 상태의 개념은 확인된 사실처럼 답변에 사용하지 않는다.

## 승인 기록 형식

사용자는 각 ID를 `승인 / 수정 / 보류 / 반려` 중 하나로 결정하고, 수정이면 원하는 뜻을 적는다. 기록에는 이 문서의 기준 커밋, 사용자 결정 날짜와 이유를 남긴다. 모든 항목이 닫히면 온톨로지/스펙 YAML과 관계 계약을 동기화하고 원천 검증·도구/문서 시험을 실행한다. **그 후에만 D1과 전체 설계 폐쇄를 판정한다.** 개별 사실/관계의 `verified` 승격은 해당 원천 스냅샷에 대한 별도 검토로 남긴다.
