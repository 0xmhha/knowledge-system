# 이웃 순위와 남은 병목 (2026-10-27)

[앞 진단](../diagnosis-2026-10-27/README.md)은 그래프가 찾은 정답 호출자가 Stage 4 이웃 칸에 들지 못한다고 끝났다. 이 문서는 그 원인을 확인하고 고친 기록이다. 같은 날 남은 병목 후보 세 가지(의도 판정, 미분류일 때의 문서 강등, 팩 칸 수)도 오프라인으로 쟀다. 모든 수치는 DEV 근거다. 사람의 표본 확인은 아직 없다.

기준은 `final`(커밋 `0c509daa`로 잰 값)이다. 지표는 앞 진단과 같다. 정답 범위와 겹치는 인용이 팩에 있으면 "정답이 팩에 있다"고 센다.

## 1. 결론

- 고친 것: Stage 4가 점수 동점을 파일 이름 순으로 다시 정렬하던 결함(`91947285`), Stage 3 이웃 중 시험 파일을 강등하지 않던 결함(`687a9662`).
- 정답이 팩에 있는 시나리오: qwen3 51 → 54, bge-m3 58 → 58(2건 얻고 2건 잃음). MRR, go-stablenet 두 갈래(PR 본문, 한국어 질문)는 그대로다. 토큰은 `final`보다 약 10% 늘었다.
- 미리 정한 규칙 2("두 모델 모두 증가")를 넘지 못해, 사용자가 결함 수정 예외로 채택했다. 원문: "A. fix-d45 채택 (Recommended)".
- 질문과의 벡터 관련도로 이웃 순위를 매기는 설계는 측정 전에 기각했다. 정답 이웃을 가려내지 못한다(3장).
- 정답 의도를 그대로 넣어도 정답이 팩에 든 시나리오는 +1, -1이다. 의도 판정 개선은 이 표본에서 얻을 것이 없다(5장).
- 팩 칸 수를 12에서 16으로 늘리면 정답 +4(qwen3), +2(bge-m3), 토큰 약 +33%로 예상된다. 토큰 판단은 사용자가 한다(5장).

## 2. 원인

이웃만으로 정답에 닿았는데 Stage 4에서 잘린 시나리오는 qwen3 4건, bge-m3 6건이었다. 정답 이웃의 Stage 3 순위는 1~37위, 팩이 이웃에 준 칸은 1~4개였다. 세 가지가 겹쳐 있었다.

- **D4. Stage 4가 Stage 3 순서를 버린다.** Stage 4는 시드와 이웃을 점수로 합친 뒤 동점을 파일 경로와 시작 줄로 정렬했다. 한 시드에서 같은 관계로 나온 이웃은 모두 점수가 같다. Stage 3은 그 동점을 범위 크기로 이미 갈라 두었다(`stage3/scoring.go`가 이유를 적어 둠). pr-8875(bge-m3)의 정답은 Stage 3 이웃 2위였지만, 같은 파일에서 줄 번호가 앞선 짧은 범위 셋이 이웃 칸을 먼저 가져갔다. pr-8894(qwen3)의 정답은 1위였고 파일 이름에서 `rpc_util.go`에 졌다.
- **D5. 시험 파일 이웃은 강등되지 않는다.** Stage 2는 의도가 test_add가 아니고 질문이 시험을 묻지 않으면 시험 파일을 ×0.25 한다. Stage 3 이웃에는 이 강등이 없다. pr-8792(qwen3)에서 정답 호출자 위 이웃 20개 중 19개가 그 시드를 부르는 시험 함수였다.
- **D6. 한 줄짜리 필드 이웃이 몸체 함수와 동점이다.** `defines` 가중치 0.5는 ArchExplain에만 있다. pr-9100에서 정답 위에 `defines` 이웃 5개가 있었다.

## 3. 기각한 설계: 질문과의 벡터 관련도

이웃마다 질문과의 유사도를 색인의 벡터로 직접 계산했다([tools/relprobe.py](./tools/relprobe.py)). 점수는 ckv와 같은 식(`1 - L2/2`)이고, pr-9003에서 ckv 출력과 소수 넷째 자리까지 같았다. 잘린 10건 중 8건에서 정답 이웃의 관련도 순위는 8~38위였다(나머지 2건은 1위, 4위). 한 줄짜리 필드 청크가 오히려 가장 높았다(pr-9100: 0.577, 정답 0.522). 관련도 순으로 바꾸면 3건, 1건을 얻고 0건, 2건을 잃는다([offline/sim-neighbor-order.txt](./offline/sim-neighbor-order.txt)). 이 정답들은 애초에 벡터 순위 29~380위(1건은 1,000위 밖)라 Stage 1에서 빠졌다. 같은 신호를 이웃에 다시 써도 가려낼 수 없다.

## 4. 측정

측정 전에 [계획](./NEIGHBOR-RANK-PLAN.md)과 판정 규칙을 고정했다. 오프라인 시뮬레이션은 시드와 이웃 칸 수를 실제 팩 그대로 두고 이웃 순서만 바꾼다. 기준 순서로 돌리면 실제 결과(51, 58)를 정확히 재현한다. 변형 3개는 실측이 시뮬레이션과 시나리오 단위까지 같았다.

| 변형 | qwen3 정답 / 토큰 | bge-m3 정답 / 토큰 | go-stablenet PR 본문 r@10 / MRR | 한국어 질문 r@10 / MRR |
|---|---|---|---|---|
| final | 51 / 1,485 | 58 / 2,866 | 0.71 / 0.73 | 0.44 / 0.60 |
| fix-d4 | 53 / 1,829 | 57 / 3,471 | 0.71 / 0.73 | 0.44 / 0.60 |
| fix-d45 | 54 / 1,633 | 58 / 3,164 | 0.71 / 0.73 | 0.44 / 0.60 |
| fix-d456 | 55 / 1,800 | 58 / 3,221 | 0.71 / 0.73 | 0.44 / 0.60 |
| final2 (커밋 `687a9662`) | 54 / 1,633 | 58 / 3,164 | 0.71 / 0.73 | 0.44 / 0.60 |

- `fix-d45`에서 얻은 시나리오: qwen3 pr-8792(D5), pr-8886, pr-8894(D4). bge-m3 pr-8869(D5), pr-8875(D4).
- bge-m3에서 모든 변형이 잃은 시나리오: pr-8979, pr-9070. 둘 다 파일 이름 순서 덕에 맞았다. pr-8979는 정답 범위가 파일 이름 순으로 첫째였고, 범위 순으로는 더 긴 이웃 넷이 앞선다(이웃 칸 1개). pr-9070은 정답 범위 안의 한 줄짜리 이웃(`config_selector.go:120`)으로 맞았다.
- 토큰이 늘어난 이유: 동점일 때 긴 범위를 먼저 고른다. D5가 그 일부를 되돌린다.
- D6는 qwen3 1건(pr-9008)을 더 찾지만 qwen3 토큰이 10%p 더 든다. 채택하지 않았다.
- `final2`는 커밋한 트리를 깨끗한 worktree에서 빌드했다([builds/final2/sha256.txt](./builds/final2/sha256.txt)). 팩이 `fix-d45`와 200건 모두 같다. MRR은 qwen3 0.281, bge-m3 0.317(벡터만 0.292, 0.291).

## 5. 남은 병목 후보 (오프라인, 코드 변경 없음)

`fix-d45`의 디버그 기록 위에서 쟀다. 시뮬레이션이라 실측과 1~2건 어긋날 수 있다.

- **의도 판정.** 가장 가까운 앵커로 고르면 정답률이 qwen3 0.37, bge-m3 0.29다(6개 의도의 기저율 0.23). 1위와 2위 유사도 차이는 맞힐 때와 틀릴 때가 같다(중앙값 0.032, 0.034). 그래서 문턱값을 모델 척도에서 떼어 내도 틀린 의도가 늘 뿐이다. 진단으로 시나리오의 정답 의도를 `intent:`로 넣어 `bin-final`을 돌렸다([tools/run_oracle_intent.sh](./tools/run_oracle_intent.sh), 사본 시나리오는 작업 디렉터리에만 있음). 정답이 팩에 든 시나리오가 qwen3 51 → 52(+2, -1), bge-m3 58 → 57(+2, -3), 팩 MRR 0.277 → 0.283, 0.315 → 0.314였다. 의도가 맞아도 팩이 거의 달라지지 않는다.
- **미분류일 때의 문서 강등.** qwen3 팩에서 문서가 시드 113칸을 차지한다. 미분류 의도에서도 문서를 ×0.5 하면 그 칸은 거의 비지만, 늘어나는 정답은 qwen3 1건(pr-8812), bge-m3 0건이다([offline/sim-doc-demotion.txt](./offline/sim-doc-demotion.txt)).
- **팩 칸 수.** 남는 칸을 Stage 2 다음 시드에 주면 아래와 같다([offline/sim-pack-slots.txt](./offline/sim-pack-slots.txt)). 칸당 평균 토큰은 qwen3 136, bge-m3 267이다.

| 칸 수 | qwen3 정답 / 추가 토큰 | bge-m3 정답 / 추가 토큰 |
|---|---|---|
| 12 (지금) | 54 / 0 | 58 / 0 |
| 16 | 58 / 약 544 | 60 / 약 1,067 |
| 20 | 62 / 약 1,089 | 63 / 약 2,133 |
| 30 (Stage 2 상한) | 63 / 약 2,449 | 65 / 약 4,800 |

후보에 오르지 못한 정답(qwen3 33건, bge-m3 25건)은 이 셋 어느 것으로도 닿지 않는다. 질문의 한국어 표현과 코드 낱말 사이의 거리가 남는다.

## 6. 확인하지 않은 것

- 사람의 표본 확인. 결과는 DEV 근거다.
- knowledge-system 자체 평가. 지금 HEAD에 맞는 색인이 없다.
- 팩 칸 수와 문서 강등의 실측. 오프라인 시뮬레이션만 했다.
- 오라클 의도 실행의 공식 요약. `retrieval_eval_summary.py`가 결과에 `expected_intent`가 있다고 가정해 실패했다. 정답이 팩에 들었는지는 `retrieval_found_diagnosis.py`로 따로 냈다.

## 7. 파일

- `NEIGHBOR-RANK-PLAN.md`: 측정 전에 쓴 계획과 판정 규칙, 그 뒤에 덧붙인 결과
- `results-table.txt`, `neighbor-rank-results.json`: 변형별 표와 얻고 잃은 시나리오
- `offline/`: 시뮬레이션과 탐침 출력
- `builds/<변형>/`: `cks` 빌드 해시와 기준 커밋 대비 diff
- `grpc-go/<변형>/`: 시나리오별 손실 분류, 요약, 팩 차이
- `go-stablenet/<갈래>/score.txt`: PR 본문(`<변형>`), 한국어 질문(`ko-<변형>`)
- `tools/`: 탐침, 시뮬레이션, 빌드와 실행 스크립트
- 저장소 밖: 전체 디버그 기록과 관련도 탐침 결과(`relprobe-*.json`, 1.5MB)는 `knowledge-data/grpc-go-retrieval-eval/eval-<변형>/`에 있다. 해시는 `manifest.json`에 있다.
