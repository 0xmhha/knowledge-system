지원 규칙과 완전한 독립 정답·매칭 공백
- 명령 규칙은 이름이 exec인 selector의 Command arg0/CommandContext arg1인 직접 identifier를
  named scalar parameter까지 lexical def-use로 역추적한다. 후속 인자·shell 문자열·PATH 신뢰·
  공격자 제어·실제 외부 함수 binding을 판단하는 취약점 탐지기로 간주하지 않는다.
- 변환 규칙은 strconv.Atoi/ParseInt/ParseUint의 두 lhs 중 두 번째가 _인 첫 결과 occurrence에서
  explicit return의 직접 identifier까지 추적한다. 오류 변수를 나중에 무시하거나 alias/closure/
  return expression/bare return을 쓰는 경우의 의미 위험과 지원 candidate 정답을 구분해야 한다.
- sanitizer 효과·spoofed owner·외부 target/import alias·memory/field/closure·실행 가능성은
  미확인/미지원이다. 문법 후보 없음과 의미상 안전을 같은 음성 집합으로 묶지 않는다.
- 통제 40개·프로젝트 68개 모두 exhaustive_candidate_gold와 independent_label은 null이다.
  미작성 gold를 빈 승인 집합이나 음성으로 바꾸지 않는다. 독립 검토자가 포함/제외/unknown
  근거·원문 source/sink·지원 범위·분기/조건을 완전하게 작성해야 한다.
- 후보 ID에는 pack/node/snapshot/source/rule/정의/사용이 포함된다. snapshot 간 정답을 단순
  candidate ID equality로 매칭하지 않는다. project/commit/file/function hash·canonical identity·
  source/sink byte/line·rule/version/digest/engine와 witness/조건·허용차·dedup을 동결해야 한다.
- 규칙별/전체 혼동행렬, 다중 후보 평가 단위, case/family 집계, base partial/rule incomplete,
  상한/timeout/미지원/unavailable/stale/기권·빈 결과의 분모·coverage 처리도 미동결이다.
- 기본선·동일 limits·정답/매칭·표본 충분성·DEV/FINAL과 precision/recall>=0.80 제안의
  수용 의미를 F-01~F-08로 확정해야 한다. 이 단계에서 기준/임계치를 변경하지 않았다.

실제 명령·호출자 계약
- 두 관측 후보 CALL-045/046은 같은 internal/build/util.go의 MustRunCommand 및
  MustRunCommandWithOutput wrapper다. 서로 다른 독립 결함/공격자 제어 양성으로 승인하지 않는다.
- 두 wrapper는 exec.Command(cmd,args...)를 MustRun에 넘긴다. MustRun은 출력 후
  DryRunFlag=false에서 cmd.Run을 호출하고 오류는 log.Fatal로 전달한다. WithOutput의
  ticker/goroutine/defer 정리 원문도 있지만 실제 자원 수명/오류 종료를 실행 검증한 것은 아니다.
- 기존 호출자 관측은 두 파일의 문법 참조 14개이며 resolved/exhaustive call graph가 아니다.
  문자열 명령 13개(docker 10, debsign/git/makensis.exe 각 1)와 linter identifier 1개다.
  alias/function value/동적/외부 호출자·실제 binding은 별도 확인이 필요하다.
- literal 이름은 PATH·실행 파일 내용·후속 인자·외부 도구 정책의 안전성을 증명하지 않는다.
  linter는 cachedir, version/OS/arch, checksum/download/archive 해제 후 경로를 반환하는 문맥이다.
  checksum/archive 구현·파일 내용/권한·cachedir 신뢰·공격자 제어에 대한 독립 실행 근거는 없다.
- build/ci.go의 none constraint·명시적 go run 설명과 lint/docker/debsrc/nsis dispatch는
  실제 CI/service 도달성 증명이 아니다. 이 단계에서 target 명령·다운로드·빌드를 실행하지 않았다.
- project commit 0bf2f4d1bfeb6605006d556957ef8c045d8f8ed8의 기존 34파일 Git 증명을
  재사용하여 68호출 span과 caller 문맥을 원문에 대조했다. 분모는 68개로 유지한다.

MCP·public client·소비자 경로와 구체적 불일치
- 현재 구현/채택 consumer의 근거 14곳을 line/byte/span SHA로 연결했다. 현재 source 10파일의
  SHA를 기록하고, 채택 consumer 2파일은 기존 채택 SHA와 Git commit→tree→blob으로 증명했다.
- CKG rule_candidates는 safeReader→strict DecodeRuleQueryInput→QueryRules 경로이며,
  CKS context.rule_candidates는 동일 schema와 optional ValueAnalysisClient를 사용한다.
  backend가 불가하면 unavailable이며 결과를 안전 음성으로 만들지 않는다.
- Query는 retained manifest·정확한 함수/blob·private path 경계·분석 후 재확인을 사용한다.
  expected_commit/source/snapshot pin은 API에서 선택적이다. 정식 수용 실행은 값과 자료를
  사전 동결하고 실제 요청에 pin을 명시해야 한다. API 자체가 필수 pin을 강제한다고 쓰지 않는다.
- 기본 standalone 이름은 bare rule_candidates이며 namespace root가 있으면
  root.context.rule_candidates다. deploy 이름·SDK alias·설치 backend와 실제 역할 호출을 확인한다.
- consumer contract의 cks_context_rule_candidates input/description은 현재 CKS metadata와
  일치하며 wire_name은 cks.context.rule_candidates다. metadata parity는 실행 성공이 아니다.
- 구체적 공백 ROLE-RULE-TOOL-01: 채택 Analyzer 본문 §7은 실제 rule_candidates 응답을 요구하지만,
  frontmatter의 명시적 tools 목록에는
  mcp__plugin_coding-agent_cks__cks_context_rule_candidates 항목이 없다.
  이 본문/목록 차이를 해소하고 실제 유효 도구 노출·권한·호출·typed 결과/handoff를 검증해야 한다.
  Bash가 있다는 이유로 직접 MCP 도구가 허용된다고 보거나 실제 호출이 반드시 거부됐다고
  단정하지 않는다. effective_host_permissions와 실제 installed role receipt는 null이다.
- 외부 consumer checkout은 변경하지 않았다. 이 발견은 후속 수정·채택·설치 연결 검증의
  구체적인 입력이다. 이번 작업은 공백 점검이며 새로운 host/프로젝트 MCP 실행은 0건이다.
